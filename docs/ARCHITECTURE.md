# Rolepay architecture

Rolepay runs pay runs for the people who run a Discord community (mods, staff, bounty winners) on Tempo. An admin builds a run, a treasurer approves it with one button, and everyone is paid in one batched stablecoin transaction. Each payout line carries a memo, recipients pay no gas, and the run exports to CSV.

This document covers the whole system. `packages/core`, `packages/discord`, `packages/web` and `apps/server` exist and are tested end to end: in process, on Moderato, and in a real browser with a virtual passkey authenticator (recipients claim with a passkey; the treasurer's passkey creates the treasury and signs the bot key's authorisation and its revocation).

## Trust model

- **The community's own Tempo account (the treasury) holds the funds.** Its root key is the treasurer's passkey (or a multisig later), created on the setup page. Rolepay never holds it in production: the browser signs with it, the server only reads the result from the chain.
- **The bot holds only an access key**, authorised by the root through the Account Keychain precompile with three restrictions:
  - an expiry,
  - a per-token spend limit (one-time or per period),
  - a call scope: only `transferWithMemo` on the payout token, optionally only to an allowlist of recipients. A community that pays people in their preferred stablecoin (off by default) adds exactly the DEX's `swapExactAmountOut` and `transferWithMemo` on each preferred token, each token under its own limit (see Preferred stablecoins).
- A leaked bot key can therefore spend at most its budget per period, only through `transferWithMemo`, until it expires or the root revokes it (a key valid for several periods can spend once per period). Replacing the key revokes the old one on chain in the same transaction, so there is one live key, and the server destroys the old key's sealed secret. The protocol enforces the limit inside a batch, with Rolepay's own checks skipped: `packages/core/test/protocolLimit.chain.test.ts` sends an over-limit batch straight to Moderato and the chain reverts it whole (`SpendingLimitExceeded`), paying nobody. The call scope and the revocation hold the same way (`packages/core/test/protocolKey.chain.test.ts`): a plain `transfer`, a `transferWithMemo` on another token and an `approve` each revert with `CallNotAllowed`, and a revoked key's transfer is refused at submit (`KeyAlreadyRevoked`), with nothing moved.
- **A standing policy can have its own access key** ("its own budget"), authorised by the same passkey with the same three restrictions and its own numbers. That policy's runs are then signed with its key and only its key, so a buggy or compromised policy can spend at most that key's budget, whatever the bot key has left; revoking it stops that policy alone. Off by default: a policy without one pays from the bot key. `packages/core/test/policyKey.chain.test.ts` shows on Moderato, with Rolepay's checks skipped, the chain refusing a batch over the policy key's remaining limit while the bot key, with plenty left, pays the same shape. See "Policy keys" below.
- **Fees** are paid by a sponsor (the public sponsor on testnet) or from a separate fee-budget token with its own limit. Never from the payout token under the payout limit: the fee would silently eat the payout budget.
- **Recipients register before they are paid.** `/payee link` issues a one-time link. On the claim page the recipient either creates a passkey account, registered at the address of the passkey session the server verified, or uses a wallet they already have on Tempo, registered at the address the server recovers from the wallet's signature over a single-use message (see "A wallet they already have"). Never an address the page sends. There are no pre-funded claim links.

The threat model (assets, actors, trust boundaries, each threat with its mitigation and what is left, and what the chain guarantees against what the code guarantees) is [`docs/THREAT-MODEL.md`](THREAT-MODEL.md).

These rules are enforced by `packages/core/test/architecture.test.ts`, not by memory. The same file checks that the package root exports no adapter and that nothing outside core reaches into core internals.

**Public surface.** `@rolepay/core` exports `createRolepay(deps)` (returns the services: `communities`, `payees`, `payRuns`, `proposals`, `policies`, `policyKeys`, `scheduler`, `audit`, `aiUsage`, `funding`, `live`), the services' types and input schemas, domain types and schemas, port types, config and constants. `@rolepay/core/adapters` exports the implementations, for composition roots only. `openRolepayAdapters(parseConfig(process.env))` opens the production set (SQLite file, AES vault, Tempo chain, random IDs, system clock) and returns `{ deps, kv, close }`: `kv` is the KeyValueStore in the same database file. `deps.fundingChain` is the read-only `TempoFundingChain` (deposit addresses, below); it reads nothing until a community sets them up.

**Money for people.** `formatAmount` prints micro-units as plain digits ("999995") for everything read back: CSV, memos, JSON, the Edit form's lines, a form field. `displayAmount` adds thousands separators ("999,995", up to 6 decimals trimmed) for what people read: Discord embeds (`views/format.ts` `money`), the dashboard (`dashboard/views/format.ts`, the charts) and the setup and account pages (`displayMicros` in `client/dom.ts`, as the bundle cannot import core). Not yet grouped: the policy rule sentences (`describeRule` in `domain/policy/policy.ts` and the dashboard's rule words in `apps/server/src/policySeam.ts`) and the audit summaries, whose text also goes into the audit CSV.

**Results, not throws.** Every expected failure is a value: `{ ok: false, error: { code: 'snake_case', ... } }`. Services throw only for the unexpected (a database or RPC outage), which the caller treats as "try again".

**No orchestrator layer.** Larger codebases put multi-service flows in an orchestrator layer. Rolepay has few flows that span services, so services read the repositories they need directly (a pay run reads communities, keys and payees; the weekly totals read which policy run made each run) but each entity is written only by its owning service. `ProposalService` is the one service that calls others: it reads the key's remaining budget through `CommunityService` and turns a proposal into a run through `PayRunService.create` and `submit`, so runs are still written only by their own service. `PolicyService` and `SchedulerService` follow the same rule: they read what they need, make runs only through `PayRunService.create`, `submit`, `approve` and `execute`, read the key budget through `CommunityService`, and share one criteria runner (`services/criteriaRunner.ts`) with criteria mode, so a policy is evaluated by exactly the code a proposal is. Add an orchestrator layer the day a flow genuinely spans more services than that.

## Domain model

Everything is keyed by the Discord guild ID: a guild is a community.

- **Community**: guild ID, name (read from Discord by `/rolepay setup`), network, treasury address, payout token, fee mode (`sponsor` or `fee_budget`, with a fee token), approver role ID (the Treasurer role the Discord layer checks), `requireSeparateApprover` (four eyes: a run's creator may not approve it; off by default), `aiProposals` (off by default), `preferredTokens` (pay each person in the stablecoin they prefer, off by default; turned on by the treasurer on the setup page), an optional `proposerRoleId` (who may propose with AI besides the approver role), and the treasury channel (`treasuryChannelId`, null = none, and `treasuryChannelSource`: `unset` while nobody chose, `found` when Rolepay picked a channel named "treasury", `chosen` when a Treasurer chose one or none; see "The treasury channel"). Changing the last two follows the same rule as the approver role. Changing the approver role, the fee mode or `requireSeparateApprover` needs a member who holds the CURRENT approver role (with none set yet, one who holds the new role): `canChangeApprovalRules` in the domain, enforced by `CommunityService` from the roles the caller passes, so Manage Server alone cannot make itself the approver.
- **SetupLink**: a short-lived (30 minute) link to the treasurer's setup page for one guild, issued by `/rolepay setup` to a member with Manage Server and the approver role. Only a fingerprint is stored. It carries the settings that first setup chose (name, payout token, fee mode, approver role), because the community cannot be registered until its treasury exists. It is not consumed on use (the page takes several steps); instead `bindTreasury` registers the treasury once and refuses any other address afterwards, and every later change also needs the treasury's own passkey session (checked by the web layer) or its signature on chain.
- **BotKey**: the bot's access key for one community. Address, sealed secret (encrypted by the KeyVault, bound to the community and key; `null` once the key is revoked or replaced, because Rolepay destroys a secret it will never use again), status (`pending_authorization`, `active`, `revoked`, `superseded`), and the policy the root signed: limit, period, expiry, optional recipient allowlist (`null` = none, the v1 default), optional fee budget, and optional `swapTokens` (the preferred stablecoins it may deliver; absent = no swaps).
- **PolicyKey**: a standing policy's own access key (`domain/policy/policyKey.ts`): the BotKey's shape and statuses plus the policy it belongs to, sealed by the KeyVault under its own context (`policy-key:<guild>:<policy>:<key>`, so a row moved to another policy, or read as a bot key, does not open). Kept apart from the bot keys, so nothing that retires or rotates the bot key touches it. Written only by `PolicyKeyService`.
- **Payee**: (guild, Discord user) to the address they are paid at, how it was proven (`addressKind`: `passkey`, the account of the passkey they created on the claim page, or `external`, a wallet they already have, proven by its signature), and optionally the USD stablecoin they want to receive (`preferredToken`, null = the payout token).
- **LinkToken**: a one-time registration link. Only an HMAC fingerprint of the token is stored, so a database reader cannot hijack a link and redirect someone's pay. It keeps the Discord username of the member it was issued to (from the signed interaction; null when Discord sent none that fits a username), which names their passkey (below), and the live nonce for a wallet claim (one at a time, with when it was issued).
- **Run**: lines (1-based, each with payee, address, amount in bigint micro-units, its bytes32 memo, and for a line paid in the payee's preferred stablecoin its `swap`: the token delivered and the most of the payout token it may spend), total, status, actors and timestamps, attempts, the paying tx, a failure if any, and a version for compare-and-set.
- **Policy**: a standing rule (see Standing policies): the original instruction next to the rule the AI compiled from it once (criteria and amount plan), the schedule, caps, mode (`propose` or `autopilot`) and veto window, status (`draft`, `active`, `paused`, `archived`), the current version and who approved it when, and a `rev` for compare-and-set. **PolicyVersion**: every version of the definition, kept for good, with its author, approval or discard. **PolicyRun**: one run of a policy for one period (unique per policy and period), linked to the pay run it made, with what code computed, the hold reason if any, the veto and the release. **AuditEvent**: the append-only audit stream (below).
- **Proposal**: a draft run the AI helped write (below): its lines with reasons and sources, held lines with why, people who are not registered, the criteria and amount rule (criteria mode) or the messages read (message mode), problems, the remaining key budget, how it was drafted (`drafted`: the model, the call's latency and its estimated cost, for the proposer's footer), a status (`open`, `run_created`, `discarded`) and an expiry a day out.
- **DepositMaster, FundingSource, Deposit** (`domain/funding.ts`, see Funding with attribution): the treasury's registration as a TIP-1022 virtual-address master (its 4-byte masterId, the registration transaction and block, and the deposit watcher's cursor); a named funding source with its 6-byte user tag and the deposit address derived from both; one deposit attributed to a source (token, amount, sender, transaction, log index, block and its time). No field but a source's name holds anyone's words, and the name is never audited or logged.
- **AiUsage**: one row per model call (`domain/aiUsage.ts`): the community, the purpose (`proposal_messages`, `proposal_criteria`, `policy_compile`), who asked, the model, the tokens (uncached input, cache writes, cache reads, output), the latency, the estimated cost in micro-dollars, the outcome (`proposed` for a drafted proposal or a compiled rule, else the error code) and when, with nullable links to the proposal, the pay run it became and the policy version a compile made. No field holds text (a test pins the field list). See AI spend below.

### Run state machine (`domain/run.ts`, pure)

```
draft --submit--> pending_approval --approve--> approved --start_attempt--> executing
executing --record_signed--> executing            (once per attempt)
executing --mark_paid--> paid
executing --mark_failed--> failed --start_attempt--> executing   (only if retryable)
failed --mark_paid--> paid | --mark_failed (partial_match, transfer_mismatch)--> failed
                                                  (the chain shows the run's memos after all)
draft | pending_approval | approved | failed --cancel--> cancelled
```

Illegal transitions return `{ ok: false, error: { code: 'illegal_transition' } }`; every (status, event) pair is tested. Failures where money may have moved (`partial_match`, `transfer_mismatch`) are never retryable: a human looks.

### Memo scheme (`constants/memo.ts`, `domain/memo.ts`)

| Bytes | Content |
| --- | --- |
| 0-1 | `"PR"` |
| 2 | version 1 |
| 3 | reserved |
| 4-27 | run ID, printable ASCII, up to 24 chars |
| 28-31 | line number, uint32 big-endian |

The memo is an indexed topic of `TransferWithMemo`, so "was line N of run R paid?" is one RPC log filter. Memos are public, so reconciliation only counts transfers from the treasury in the run's tokens: the payout token, and the preferred stablecoin of any swapped line. Each line must be paid in its own token (`lineToken`); its memo in another of the run's tokens is a mismatch for a human.

## Never pay twice

`PayRunService.execute` and `reconcile` rest on three facts:

1. **One owner per attempt.** A run moves `approved -> executing` by compare-and-set on its version. A second worker (or a double click) gets `concurrent_update` and sends nothing.
2. **Persist before broadcast.** The adapter signs the batch without broadcasting; the service stores the signed tx and its hash; only then is it broadcast. Re-broadcasting the same signed tx can land it at most once.
3. **A deadline for every attempt.** Each attempt fixes `validBefore` (now + 120 s, an expiring nonce) before signing. Once chain time passes it, that tx can never land, and no new attempt starts before then.

Paying people in their preferred stablecoin changes none of this: the DEX swaps are calls in the same atomic batch, signed, persisted before broadcast and bound by the same deadline as the transfers; a swap that fails reverts every transfer with it; and each line is still found by its own memo, in the token it delivers (the swap itself emits no memo transfer). The quotes and limit reads before signing only decide whether to start an attempt.

`reconcile` never signs anything new. In order: look up the recorded tx hash; otherwise read the chain head, then search memo transfers (in every token the run delivers in, `runTokens`) from the first attempt's start block up to THAT head's block; if nothing is found and that head's timestamp has not passed the deadline, re-broadcast the same signed tx (or report `pending`); once it has passed with nothing on chain, mark the attempt `not_landed`, which makes a fresh attempt provably safe. Reading the head first matters: a search followed by a separate head read could miss a tx that landed between the two and call a paid run `not_landed`.

**One worker per run at a time.** The Approve job, the recovery sweep and another instance never work on the same run at once. Each `execute`, `reconcile` and swept run holds the run's lease (the `RunLeases` port; `KvRunLeases` on the SQLite file in production, atomic create-if-absent, 180 seconds, given back when the step ends); a worker that finds the run held gets `concurrent_update` at once and sends nothing. The sweep also skips the runs its caller names (the server's own queued or running jobs, waits between checks included) and reads each run again once it holds it, so a run settled since the listing is left alone instead of raced. A lease left by an earlier process of the same machine (a crash) is taken over at once; one held by another machine is respected until it expires. Leases only stop duplicate work and spurious conflicts: the compare-and-set, the persisted tx and the deadline above are still what make a double payment impossible, with or without them. (Seen on the demo on 2026-10-07: the 30-second sweep picked up a run 1.8 s after Approve, while its job was paying it, and lost the race to record the result, logging `concurrent_update`. The run was paid once, by the job.)

**A new attempt waits until the last one can no longer land.** Before a retry (and before cancelling a failed run), `execute` reads the chain head and, while its timestamp is not past the last attempt's validBefore plus the margin, returns `pending` with `retryAfter` (cancel returns `attempt_may_still_land`); the Discord job waits and asks `execute` again. This costs at most about 130 seconds, only after a failure, and it makes "never pay twice" independent of how a node's error text was classified: a broadcast misread as "rejected" while the tx sat in a mempool can still land, but never beside a second attempt. The fake chain models exactly that (`reject_but_keep_pending`, then `mine()`).

Then `execute` checks the chain once more, up to that head. If any of the run's memos are there it sends nothing and records what the chain shows: all of them, and the run is `paid` (receipts go out as usual); some, or the wrong amounts, and it becomes a failure a human must look at, and `execute` returns `chain_shows_payments`. `cancel` makes the same check on a failed run and refuses (`chain_shows_payments`), so a paid run never reads "cancelled" and a person following the UI is never led to pay it again. The failure messages in Discord say what was checked ("the chain shows nothing paid for this run"), never "nothing was paid".

| Crash point | State left behind | Recovery |
| --- | --- | --- |
| after opening the attempt, before signing | `executing`, no tx | nothing was signed; after the deadline, `not_landed`, then retry |
| after signing, before recording | `executing`, no tx | nothing was broadcast; same as above |
| after recording, before broadcast | `executing`, signed tx | reconcile re-broadcasts the same tx |
| after broadcast, before recording the result | `executing`, signed tx | reconcile finds the receipt or the memos, marks `paid` |

`PayRunService.recoverInFlight()` reconciles every `executing` run; the server runs it on boot and on an interval. The crash cases are tested with fakes, on a real SQLite file, and on Moderato.

**Which key signs is decided per attempt, after all of the above.** `execute` picks the signing key (`signingKey` in `payRunService.ts`) only once the run is `approved`, or a failed run's last attempt can no longer land and the chain shows none of its memos: a run a policy made (its PolicyRun links it) is signed with that policy's own key once one is authorised, every other run with the community's bot key. Nothing in the three facts depends on which key that is: the compare-and-set is on the run's version, the stored tx is re-broadcast as signed (reconcile and the recovery sweep never need a key), the deadline is the attempt's, and the memo search is by run memos from the treasury, in every token the run delivers in, whichever key sent them. The pre-flight below (the payout limit with each swapped line at its maximum input, then the swap scope, quotes and preferred-token limits) runs on the key chosen here, and a refusal on a policy's own key carries `key: 'policy'`. Both keys use expiring nonces, so a bot key run and a policy key run can be in flight on one treasury at once. A retry may be signed by a different key than the attempt before it (a policy given its own key in between); that is safe for the same reason any retry is: it starts only after the last attempt provably cannot land. A policy whose own key was revoked is refused (`key_revoked` with `key: 'policy'`) and never falls back to the bot key.

Before signing, `execute` reads the key from the chain (`checkKeyForRun`): revoked, expired, expiring inside the submission window, or a run larger than the remaining limit all fail fast with a clear code. Without this, a revoked key fails late and vaguely (the spike saw about 110 s and "Missing or invalid parameters").

## Bot key lifecycle

1. `CommunityService.provisionBotKey` mints a fresh secp256k1 key, seals the secret, stores it as `pending_authorization`, and returns the exact authorisation for the root to sign (expiry, limits, scope). On the setup page the treasurer chooses the limit, the period and the expiry (and the fee budget in `fee_budget` mode).
2. **Production:** the browser sends a Tempo transaction from the treasury to the Account Keychain (`accessKey.authorize`), signed with the treasurer's passkey (WebAuthn P256) and sponsored on testnet; then `confirmBotKey` marks the key active once the chain shows it. **Dev, CLI and tests:** `authorizeBotKey({ root })` signs with an in-process `RootSigner` (`rootSignerFromPrivateKey`), then confirms (`pnpm dev:authorize-key`).
3. Rotation: "Replace the bot key" on the setup page sends ONE root transaction whose calls revoke every key still live on chain and then authorise the new one (`rotationCalls` in `client/keychain.ts`): atomic, one signature, one passkey prompt. `confirmBotKey({ keyAddress })` confirms the key the browser named (never "the newest pending one"), marks each other key revoked when the chain shows it so, superseded otherwise, and destroys their sealed secrets. A superseded key that is somehow still live on chain is listed on the setup page with its own Revoke button. The dev path (`authorizeBotKey({ root })`) revokes the old live keys with the in-process root before authorising the new one. A revoked key ID can never be re-authorised, so rotation always mints a fresh key.
4. Revoke: the setup page lists every key live on chain (`listKeys`), each with a Revoke button, and a pending key never hides the active one (`keyStatus` prefers the active key). It signs `accessKey.revoke` with the passkey and `confirmRevocation({ keyAddress })` marks that key revoked once the chain shows it (it never trusts the caller's word) and destroys its secret. Dev path: `revokeBotKey({ root })`. `keyStatus` and `listKeys` always read the chain.

A recurring limit's period is anchored at authorisation time, not at calendar months.

## Policy keys (a policy's own budget)

Access keys are how you give software a budget it can't exceed, so a standing policy can get its own. `PolicyKeyService` mirrors the bot key's lifecycle, scoped to one policy:

1. `provision({ guildId, policyId, limit, periodSeconds, expiresAt, feeBudget })` mints a key, seals it under the policy key's context, stores it `pending_authorization` (superseding a key of this policy still waiting) and returns the authorisation: exactly the bot key's restrictions (`policyKeyAuthorization`, which is `keyAuthorization` with the policy's numbers: the one place the policy key's scope is decided), including, while the community pays people in their preferred stablecoin, the same swap scope as the bot key (`preferredTokenPolicy`, shared with `provisionBotKey`), under the policy's limit. An archived policy gets none (`policy_archived`).
2. The treasurer signs it on the treasury page for that policy (`/setup/:token/policies/:policyId`, below), one root transaction (the page builds the authorisation from its form and the page config, the swap tokens included while the switch is on, and refuses a server copy that differs); `confirm({ keyAddress })` marks it active once the chain shows it, retires this policy's other keys (revoked when the chain shows it, superseded otherwise) and destroys their secrets, and writes `policy_key.authorized`. Rotation is the same transaction revoking this policy's live key first. Dev path: `authorize({ root })`.
3. `confirmRevocation({ keyAddress })` records a revoke the passkey signed, once the chain shows it, destroys the secret and writes `policy_key.revoked`. Dev path: `revoke({ root })`.
4. `status` (whose budget pays the policy, `bot`, `own` or `retired`, and the key that matters with what the chain says), `listKeys` (this policy's keys not yet revoked, for the page's Revoke buttons) and `budget` (what the next run is held against) always read the chain.

Which key signs (`policySigner`): the bot key until the policy's own key is authorised (a key waiting for the passkey changes nothing); then that key only; and once it is revoked, nothing: the policy is stopped until it gets a new key, and never falls back to the bot key, so revoking a policy's key is a kill switch for that policy alone. The scheduler and the preview hold a policy with its own key against that key's remaining budget, swaps counted at their maximum input (`over_policy_budget`, `swaps_over_policy_budget`, `policy_key_inactive`), and a release that meets the policy key's pre-flight refusal is held in the same words (`policyKeyHold`). Manual runs, AI-proposed runs and other policies keep using the bot key. The audit stream's actor for the two key events is the member the treasury page link was issued to; the passkey signed the transaction.

Where it is offered: after Approve policy in Discord, the approver alone gets a private follow-up with a link button, "Give this policy its own budget" (a fresh setup link, 30 minutes, with the policy's path; a private follow-up is never posted in the channel instead); `/rolepay policy show` carries the link for the approver role and a Budget line for everyone ("Own budget: 20 of 30 AlphaUSD left this period (chain-enforced)"); the policy's dashboard page draws the budget and, for the Treasurer role, posts to `.../budget`, which issues the link and redirects to the page. An archived policy whose key is still live is offered the revoke there.

## Fees

- **`sponsor`**: the tx carries `feePayer: true` and is filled through a relay (`withRelay`). Testnet: the public sponsor `https://sponsor.moderato.tempo.xyz`. Mainnet has no public sponsor: Tempo's hosted one (`api.tempo.xyz/rpc/sponsor`) needs an API key with billing, or a self-hosted relay; neither is configured, so mainnet runs without one.
- **`fee_budget`**: the bot pays fees in a separate token (for example pathUSD) under its own small limit, authorised alongside the payout limit. The budget must cover gas limit times price up front (the keychain pre-charges, then nets back).
- **A server without a sponsor** (mainnet, or `ROLEPAY_SPONSOR_URL=none` to rehearse it on testnet) needs `ROLEPAY_FEE_TOKEN` (config refuses it otherwise, and refuses a fee token equal to the payout token), starts every new community in `fee_budget` mode with it, and refuses `fees:sponsor`. The treasury's own transactions on the setup page pay their fee in the fee token while the treasury holds 0.1 or more of it, otherwise in the payout token (`client/fees.ts`), so a revoke never fails for want of the fee token. A payee's transfer on the account page pays its fee in the token sent. `apps/server/e2e/mainnetPath.spec.ts` runs that whole path on Moderato with the sponsor off.
- `/rolepay setup fees:fee_budget` (or `fees:sponsor`) switches the mode; `setFeeMode` says when the active key has no fee budget for it, and the card asks the treasurer to authorise a new key with one on the setup page. A key with a fee budget keeps working after switching back to sponsored. Proven on Moderato by `packages/core/test/feeBudget.chain.test.ts` (fee paid in pathUSD, payout limit exact).
- "Sponsor down" is not automatic yet: a run fails as `rejected` (retryable), and switching the community to `fee_budget` is the fallback.

## Preferred stablecoins (pay each person in the token they choose)

A payee may choose the USD stablecoin they receive; a run then buys it for them on Tempo's enshrined stablecoin DEX (`0xdec0…`), in the same batched transaction that pays everyone. Off by default per community; with it off, nothing below happens and every authorisation, batch and receipt is exactly as before.

- **The choice.** `/payee prefer token:` in Discord (choices from a fixed list per network, `PREFERRED_TOKENS`: AlphaUSD, BetaUSD and ThetaUSD on Moderato; USDC.e, OUSD and USDT0 on mainnet; pathUSD is the fee token and never one), the claim page once the passkey registers, or the account page signed in with the passkey (`POST /account/preference`, always for the verified session's own address). `PayeeService.setPreferredToken` stores it on the payee (null for the payout token); it never changes where they are paid. A community can deliver its allowlist minus its payout token and minus its fee token (`swapTokensFor`: an access key has one limit per token, and the fee token's is the fee budget).
- **The switch.** The treasurer turns it on with the treasury passkey on the setup page (`CommunityService.setPreferredTokens`). That changes nothing on chain; the next key the page authorises carries the swap scope (`keyAuthorization` appends `preferredTokenGrants`), and until then runs with swaps are held with `swap_not_authorized` (the state endpoint says `keyNeedsSwapScope`). The same holds for a policy's own key: one provisioned while the switch is on carries the swap scope under the policy's limit; one from before cannot swap, its policy's runs with a swapped line are held (`swap_not_authorized` with `key: 'policy'`, never passed to the bot key), and the policy's treasury page says so until the treasurer gives it a new key there.
- **The line.** `PayRunService.create` fixes each line's delivery when the run is made, so the approver sees it and every attempt signs the same thing: a payee who chose another token the community can deliver gets `swap: { token, maxIn }`, where `maxIn` is the amount plus `ROLEPAY_SWAP_MAX_SLIPPAGE_BPS` (100 = 1% by default, at most 500), rounded down. The review embed shows "5 AlphaUSD → 5 BetaUSD (swapped)" and the most the swaps may spend; the run's total stays the sum of the amounts (what people receive, in USD).
- **The batch** (`buildBatchCalls`). First one `swapExactAmountOut(payoutToken, token, amountOut, maxAmountIn)` per delivered token, for the lines' amounts summed and their maxima summed (one swap per token keeps the gas near a plain run's, about 200k per swap on Moderato against about 300k per first transfer; per line the cap is the same sum). Then one `transferWithMemo` per line, in line order, each in its own token with its own memo. The DEX has no swap to a recipient (Tempo's exchange spec: the output is transferred to the caller), so the bought tokens land in the treasury and the transfer in the same transaction delivers them; the swap emits no `TransferWithMemo`, so reconciliation sees exactly one memo transfer per line. Exact output means the treasury keeps none of the bought token. No `approve` is needed: the DEX takes the input from the caller, and an approve would only charge the key's limit a second time (measured on Moderato).
- **Before signing** (`swapPreflight`, after `checkKeyForRun`, both on the key that signs the attempt: the bot key, or the policy's own key): the payout-limit check counts each swapped line at its `maxIn` (`payoutSpendCap`); the key must have been authorised for every delivered token (`checkSwapScope`); each swap is quoted read-only (`quoteSwapExactAmountOut`), and no route (`swap_no_route`: no pair or not enough liquidity) or a quote above the leg's maximum (`swap_over_cap`, with the numbers) holds the run whole; and the key's remaining limit in each preferred token must cover what the run delivers in it (`swap_limit_low`). A held run stays `approved` with Retry, nothing signed, like any pre-flight failure; a policy run is held with the code. A policy's run is checked earlier too: the scheduler and the preview hold it when it is made if its swaps at their maximum would take it past what the paying key has left (`swaps_over_budget`, `swaps_over_policy_budget`; Standing policies, Guardrails).
- **On chain.** If the price moves past a leg's maximum between the quote and the block, the swap reverts with `MaxInputExceeded` and so does the whole batch: nobody is paid, the run fails as `reverted` (retryable, with the usual wait and memo check).
- **The key's limits** (`preferredTokenGrants`): `swapExactAmountOut` on the DEX and `transferWithMemo` on each preferred token, and each preferred token limited to the payout limit with the same period. Tempo charges a swap's actual input to the key's limit in the token it sells (measured on Moderato: a swap of AlphaUSD lowered the AlphaUSD limit by exactly what it took; a swap selling a token the key has no limit for reverts with `SpendingLimitExceeded`). So every unit of payout token leaving the treasury, transferred or swapped, counts against the payout limit as before, and a preferred token's limit caps what the key can send of that token. The residual is in the threat model (T25, T26).
- **Proof.** `packages/core/test/preferredToken.chain.test.ts` on Moderato: the routes, a run paying one person in AlphaUSD and one in BetaUSD in one batch (balances, memos, limits), a run held before signing over its cap, a hand-signed batch over its maximum reverting whole, and the key refused outside a run. `apps/server/e2e/passkeys.spec.ts`: the switch and the swap scope signed with a real passkey and read back from the chain, and a BetaUSD payout from a passkey treasury.

## Persistence

SQLite through Kysely and better-sqlite3 (`adapters/sqlite/`). Proposals are not a table: they are short-lived KeyValueStore records (see AI-proposed pay runs). The schema is portable on purpose: money as exact decimal text (Postgres `NUMERIC`), timestamps as ISO text, small nested values (key policy, attempts, failure) as JSON text. Moving to Postgres means a Kysely Postgres dialect plus the same migrations, with no service changes. Migrations live inline in `migrations.ts` and are append-only. Every row read is re-validated by the domain's Zod schema.

The repository contract (`test/support/repositoryContracts.ts`) runs against both the in-memory fakes and SQLite, so unit tests on fakes can be trusted; the policy repositories and the audit log have their own (`test/support/policyRepositoryContract.ts`).

Migration `0006_policies` adds `policies`, `policy_versions` (primary key policy and version), `policy_runs` (a UNIQUE constraint on policy and period key: the idempotency of the scheduler rests on it) and `audit_events` (an integer `seq` row ID, an identity column on Postgres). Nested values (the compiled rule, schedule, caps, lines) are JSON text with tagged bigints and dates, re-validated on every read.

Migration `0008_policy_keys` adds `policy_keys` (primary key the key address, foreign keys to the community and the policy, the sealed secret nullable once destroyed, the key policy as JSON text, indexes on policy and community). A new table only, apart from `bot_keys` on purpose; a test builds a database with the migrations up to 0007, fills it (a community, its bot key, a run, a policy) and opens it with the current code.

Migration `0009_preferred_tokens` adds columns only, nullable or with a default, so it applies to a database with data: `communities.preferred_tokens` (0, off), `payees.preferred_token` (null, the payout token) with an index on `payees.address` (the account page lists an address's registrations), and `run_lines.swap_token` and `swap_max_in` (null for a line paid in the run's token; the maximum as exact decimal text). A test opens a database 0008 left (with `0008_policy_keys` applied), with communities, payees, runs, a policy and its own key in it, and reads everything back as before (the rows written with that release's columns, not today's code).

Migration `0007_ai_usage` adds `ai_usage` (an integer `seq` row ID, the cost as decimal USD text such as `0.0108`, `NUMERIC` on Postgres, and indexes on community and time, proposal and policy). It only creates a table, so it applies to a database with data in it as to an empty one; a test builds a database with the migrations up to 0006, fills it, and opens it with the current code (`migrateTo` in `migrations.ts`).

Migration `0010_funding` (numbered after `0008` and `0009`, which belong to features developed alongside it) adds `deposit_masters` (one per community, the watcher's cursor in `scanned_to`), `funding_sources` (a UNIQUE constraint on community and user tag: two creates racing for the same tag, one wins) and `deposits` (primary key transaction hash and log index: the watcher's idempotency rests on it). Block numbers are `BIGINT`, so the cursor moves forward only by a compare in SQL (`scanned_to < ?`); amounts are exact decimal text. New tables only; a test builds a database with every migration before it, fills it, and opens it with the current code (`MIGRATION_NAMES` in `migrations.ts`).

Migration `0011_link_usernames` adds one nullable column, `link_tokens.discord_username` (the passkey's name above), so links from before keep working and their page names the passkey with the Discord ID. A test opens a database 0010 left, with a community, a payee, a spent and a live link, a run and a funding source in it, and reads everything back as before.

Migration `0012_address_kinds` adds `payees.address_kind` (`passkey` by default, so every payee registered before is a passkey account) and the link's wallet nonce (`link_tokens.wallet_nonce`, `wallet_nonce_at`). Columns only; a test opens a database the 0010 release left (communities, payees, live and spent links, a run, a policy with its own key, a funding source), applies 0011 and 0012, and reads everything back as before. The two are separate migrations because 0011 shipped as a bug fix of its own.

Migration `0013_treasury_channel` adds `communities.treasury_channel_id` (nullable) and `treasury_channel_source` (`unset` by default), so every community from before has none and nobody chose one (Rolepay may look for a channel named "treasury"). Columns only; a test opens a database the 0012 release left (communities with every setting, payees, a run, a policy with its own key, a funding source) and reads everything back as before. `CommunityRepository.update` leaves both columns as stored: only `setTreasuryChannel` changes them, with an optional compare-and-set on what was read, so a channel Rolepay finds never overwrites a Treasurer's choice made in between. Where a run's two Discord messages are is not a column: it is in the KeyValueStore with the rest of `RunNotices` (below).

**KeyValueStore** (`ports/keyValueStore.ts`, migration `0002_key_value`): small JSON records with an optional expiry, with atomic create-if-absent and read-and-delete, for state that is not a domain entity. The web layer keeps the passkey credentials, challenges and sessions there (through the Accounts SDK's `Handler.webAuthn`, keys under `webauthn:`), and the Discord layer keeps where a run's review message is, where its copy without buttons is (with a treasury channel), whether its receipts went out, and where a policy preview's two messages are with the version they show (with a treasury channel) (`discord:`). The shape matches the Accounts SDK's `Kv`. `create` is one upsert guarded by expiry and `take` is one `DELETE ... RETURNING`, so both stay atomic on Postgres. Its own contract (`test/support/keyValueContract.ts`) runs against memory and SQLite.

## AI-proposed pay runs

**AI proposes, the protocol limits, a human approves.** A proposal is a draft. The model never approves, signs or pays: a proposal becomes money only through `PayRunService.create`, the treasurer's approval and the bot key's on-chain limit, all unchanged.

Two modes, both `ProposalService` methods:

- **Message mode** (`proposeFromMessages`): the model reads messages and the treasurer's instruction ("50 each, the indexer one 200, note: October bounties"). The source is the message a "Draft pay run with AI" command targeted (it arrives with the interaction, so no intent is needed) or a channel's or thread's newest messages (at most 200, at most 31 days back; their text needs the Message Content intent). Before anything is sent, every user ID and mention becomes a token (`U1`, `U2`, ...) and every message `M1`, `M2`, ... (`domain/proposal/sources.ts`); the map back stays in code. Names typed as plain text cannot be recognised and are sent as written, which the setup card says.
- **Criteria mode** (`proposeFromCriteria`, "pay X to people who Y"): the model sees only the instruction (with roles, channels, people and message links as tokens) and the server's role and channel names by token, never members or messages. It returns a filter and an amount rule (`domain/proposal/raw.ts`); code checks them (`resolveCriteria`), reads what they need through the `ActivityReader` port, and runs them over the registered payees (`evaluateCriteria`). People the activity shows who match but are not registered are listed with a nudge to `/payee link`.

| Filter (v1, AND of all) | Read through |
| --- | --- |
| `hasRole` (any of), `lacksRole` (none of), `joinedBefore`, `joinedAfter` | one Get Guild Member per candidate (no GUILD_MEMBERS intent) |
| `messagesIn`, `activeDaysIn` (distinct days), `repliesIn` (replies to other people's messages) `{ channels, since, until, min }` | channel history, author IDs only (no Message Content intent; View Channel and Read Message History) |
| `reactedTo { message, emoji? }`, `mentionedIn { message }` (a message linked in the instruction) | the message and its reactions |
| `postedIn { thread }` | the thread's history |
| `paidInRun { run }`, `paidInLastRun` | Rolepay's own runs |
| `neverPaid` ("first-time", "who have never been paid"): no line in one of this community's runs that paid or may pay (`paidPayees`: paid, approved or being paid, or failed in a way that may have moved money). Drafts, runs waiting for approval, cancelled or vetoed runs, failures that sent nothing and other communities' runs do not count | every run of the community, through `RunRepository.listByCommunity`; with no history read, nobody matches |
| `exclude { users }`, `excludeProposer` | |

Bounds, applied in code: at most 31 days back (a longer window is cut and the proposal says so), 10,000 messages per proposal across every channel it reads (a scan the bound stops is flagged), 5 channels, 100 unregistered people listed. The REST adapter pages history 100 at a time and waits when a rate-limit bucket empties. Not in v1: voice activity, reactions received, deep forum scans, OR between groups.

**Amount rules** (`domain/proposal/amounts.ts`, bigint micro-units throughout): `flat`, `perUnit` (per message, active day or reply, with an optional cap), `pool` (a total split by messages, active days, replies or equally), per-person overrides (they win over the rule and the cap) and an optional per-person cap. A pool is split by the largest-remainder rule: each person gets floor(total times weight, divided by the sum of weights) micro-units, and the few micro-units left over go one each to the largest remainders, ties broken by Discord user ID ascending, so the shares always add up to the total exactly and the same input always gives the same split. Overrides come out of a pool first; a pool is split among registered matches only. Message mode's "split 300 between the winners" uses the same rule.

**The checks, in code, whatever the model says** (`domain/proposal/proposal.ts`). A line is held (shown, left out of the run) when:

- every message backing it was written by the person it pays (`self_sourced`: "pay me 10,000");
- a message backing it tried to instruct the AI (`suspicious_source`; such messages are listed by author, never by text);
- no message backs it, or the model named someone who is not in the messages;
- its amount is not stated in the instruction (`amount_not_in_instruction`), or was said to come from a message and no message by someone else states it. Only numbers that read as amounts count: counts with their unit ("10 replies", "7 days"), dates, a year next to a month, ranks and references ("top 3", "#4521") are not amounts, so a line cannot borrow them;
- the person is listed twice, or the line alone is more than the bot key has left.

Then registration, the 50-line limit and the total against the key's remaining budget. Two problems block Create until an Edit: in criteria mode, an amount the instruction never stated (the instruction is the only text the model saw); in message mode, any amount taken from a message rather than the instruction, because anyone in the channel could have written it (the treasurer confirms it by submitting the lines). A message by a bot or webhook can back a line like anyone else's (bounty bots announce winners), but a bot or webhook is never paid: an author the message data marks as a bot never appears in a proposal, as a line or as left out. When every line is held as `self_sourced` ("2 each to everyone who wrote here today" read from the channel), the proposal says that is a rule about activity and offers Count who wrote, which asks again in criteria mode with the channel named, where code counts who wrote from the history (bots left out). Edit (the treasurer types `@user=amount` lines) makes the lines exactly what was typed. Create claims the proposal once (`ProposalRepository.claim`), so two clicks make one run; the claim is given back only if no run was created, so a failure after `create` (a write, the submit) can never lead to a second run.

**Who may propose.** The approver role, or the community's optional proposer role (`canPropose`), checked by core on every propose, edit, discard and create from the roles Discord signed into the interaction; the Discord layer checks first for a clear message, and the commands are hidden from members by default (`default_member_permissions`). The instruction is therefore trusted; the source messages are written by anyone in the channel and stay untrusted data. Proposing from a channel's history also needs the caller's own View Channel and Read Message History there (Discord sends their permissions in the picked channel), so the bot never reads a channel for someone who could not read it. AI proposals are off per community until a member with the approver role turns them on.

**The model** (`adapters/anthropic/`, behind the `RunProposer` port, a deterministic fake in `adapters/memory/fakeProposer.ts`): `claude-sonnet-5-5` (`ROLEPAY_AI_MODEL`) through the official SDK, one request per proposal, structured output in a JSON schema derived from the domain's Zod schemas (`outputSchema`), then validated with those same schemas. The API refuses (HTTP 400) a schema with more than 16 union-typed parameters, and each nullable field is one, so criteria mode's answer has no nulls: optional values are empty strings, and the counting windows and the message or thread conditions are lists (`activity`, `anchors`) that `resolveCriteria` maps to the filters above; a test keeps every mode's schema at 12 or fewer. No `temperature` (Sonnet 5.5 and Opus 5.5 reject it); thinking cannot be disabled (`disabled` is a 400), so effort is `low` and `max_tokens` is 16,000 to leave room after thinking. No server-side fallback: the model that answers is the model the demo names (on Sonnet 5.5 a fallback would only retry `cyber` and `frontier_llm` declines, on Sonnet 5), and a refusal is a `could_not_propose` result. **Prompt caching:** each mode's system prompt is a constant, sent as one system block with `cache_control` and the 1-hour TTL, and the API caches it together with the output schema: measured on Sonnet 5.5, 1,844 tokens in message mode and 3,689 in criteria mode, over the 512-token minimum (criteria mode measured before `neverPaid` and the line on schedules in the instruction were added, a few dozen tokens more). `neverPaid` is a plain boolean in the answer, so it adds no union-typed parameter. Everything that changes per request (the instruction, tokens, today, the lookback, the budget, messages) is in the user message after it, and a test keeps the system block and the schema byte-identical across two different requests in each mode. The TTL is one hour, not five minutes, because demo traffic is sparse: a person reads a proposal and approves it with a passkey, often more than five minutes before the next one. A 1-hour write costs 2x input ($4 per million tokens on Sonnet 5.5, about half a cent more than a 5-minute write for the criteria prefix) and a read 0.1x ($0.20), so one proposal 5 to 60 minutes after another in the same mode pays the difference back; and since a write only happens after an hour with no request in that mode, a server that never reuses the cache pays for at most about 24 writes a day per mode (at most about $0.27 a day more than not caching, both modes together). The log line carries the cache tokens, so the hit rate can be read from it. Measured with the live tests (four runs, 2026-10-07): a warm proposal costs about $0.003 to $0.004, against about $0.009 uncached, and a cold one $0.011 (message mode) or $0.018 (criteria mode); latency stayed within the run-to-run noise (warm 1.8 to 3.1 s with one 8.6 s outlier, cold 3.0 to 5.0 s), because it is mostly the answer's generation, not reading the prefix. Message text goes inside `<messages>` as JSON with `<` and `>` escaped, so no message can close its tag, and the system prompt says instructions inside it are never followed. A refusal, a cut-off or malformed answer, or an API error is a `could_not_propose` result, never a crash. Without `ANTHROPIC_API_KEY` there is no proposer and every AI command answers that AI is not configured. **A daily cap** keeps a public server from running up the bill: the production proposer is wrapped in `DailyCappedProposer` (`adapters/kv/proposerDailyCap.ts`), which lets at most `ROLEPAY_AI_DAILY_CAP` model calls (default 50) through per UTC day across every community on the server. Each call takes a numbered slot for the day with the KeyValueStore's atomic create-if-absent, so a restart keeps the count and concurrent calls never share a slot; failed calls count, because they are billed. Past the cap the model is not called and the answer is `could_not_propose` with reason `daily_cap` ("after midnight UTC, or `/rolepay new`").

**Storage and logs.** Proposals are KeyValueStore records (`adapters/kv/proposals.ts`) that expire after a day: no migration, and they move to Postgres with the store. The target of a message command is kept the same way for at most 15 minutes, until its modal is submitted. The server sweeps expired records off the disk on its recovery interval (`KeyValueStore.sweep`), so an abandoned form's message text does not stay. One `proposal` log line per attempt: mode, outcome, counts (messages sent or scanned, lines, held, unregistered), model, tokens (uncached input, cache writes, cache reads, output), an estimated cost (cache writes and reads at their own prices, `adapters/anthropic/pricing.ts`) and latency, and `timings` in milliseconds (Discord reads, chain reads, the model, the total); never message text, instructions, reasons or names. The reads a proposal needs before the model (the channel or the role and channel names from Discord, the remaining budget from the chain) run at the same time, and the names are kept for a minute per server.

**AI spend.** Every call that reaches the model is also an `ai_usage` row (the AiUsage entity above), written by `ProposalService` and `PolicyService` through the `AiUsageRepository` port: each proposal attempt in both modes and each policy compile, failures after the call included (`could_not_propose` with whatever usage came back, `criteria_unclear`, `cannot_read`). A call the model never received (refused before it, a read that failed first, past the daily cap) writes nothing. Create pay run links the proposal's row to its run (`linkRun`); a compile that worked is linked to the policy version it made. `rolepay.aiUsage` reads them back: `month` (this UTC month's estimated total, the calls on a model without a price, and the average cost of a drafted proposal, rounded half up to a micro-dollar) and `list`. Costs come from the same estimate as the log line (`pricing.ts`), not from Anthropic's bill.

- **The proposer's footer.** The proposal embed ends with `Drafted by Sonnet 5.5 · 2.1 s · $0.004` (the model as people say it, `modelLabel`; the model call's latency; the cost rounded half up, three decimals under 10 cents and `<$0.001` below that, `usdText`; the cost is left out for a model without a price). The proposal is always an ephemeral reply, and Edit updates that same message, so only the proposer sees it. The run Create posts, its review, the paid message and the receipt DMs are built from the run alone and never carry it.
- **Retention.** What is stored: the fields above, numbers, codes, IDs and the model name. It holds no text: never an instruction, a message, a name or a reason. The only person in it is the asker's Discord user ID, as in the audit stream. It is kept for good, like the runs and the audit stream it explains (no purge job): the daily cap bounds it to about 50 rows a day per server, a few hundred bytes each.

## Standing policies (the agent treasurer)

**AI writes the rule once. Humans approve it. Code runs it. The chain caps it.**

A policy is a standing rule, for example "every Monday: 1 USDC per answered question in #help, max 50 a week each, for Mods". Code is in `domain/policy/` (pure), `services/policyService.ts`, `services/schedulerService.ts`, `services/policyEvaluation.ts` and `services/auditTrail.ts`.

### Lifecycle

1. **Create** (`PolicyService.create`, from `/rolepay policy new` or the dashboard): the model compiles the instruction ONCE with criteria mode (the same request, prompt, checks and `resolveCriteria` as `/rolepay propose`, so the same daily cap and the same "the model never sees members" rule). The original instruction is kept next to the compiled filter and amount plan. The schedule and the caps are options, never parsed from the text. The policy is a draft (version 1). Who may write: the approver role or the proposer role, with AI proposals on.
2. **Preview** (`preview`): the compiled rule in plain words, the exact filter, and who it applies to right now: the period in progress (since the last occurrence) is run through the rule by code; each person comes with their counts, why they match and what the next run would pay; people who match but are not registered, and near misses (they failed only a count and had at least one), are listed apart; the total is compared with the bot key's remaining budget and the policy cap.
3. **Approve** (`approve`): only a member holding the CURRENT approver role, for the version they saw (`version_mismatch` otherwise). Recorded with who and when on the policy and its version. Blocked while the rule uses an amount the instruction does not state (rewrite the instruction). With four eyes on (`requireSeparateApprover`), the author cannot approve their own rule or switch its autopilot on.
4. **Edit** (`edit`): a new version (any of name, instruction, schedule, caps, and from an approver the mode and veto window; a new instruction is compiled again). **An approver's edit of an approved policy is in force at once**: when the editor holds the CURRENT approver role, the community does not require a separate approver and the policy is active or paused, the new version is recorded as approved by the editor (on the policy and its version), the status stays (active, with `activeSince` now, as `approve` sets it; or paused), and the mode stays unless the edit names one. Autopilot that stays or is switched on is re-endorsed by the editor (`autopilot.enabledBy`, `enabledAt`, the current approver role): its runs are approved in their name from then on. The checks `approve` makes still apply (a daily schedule without the demo controls, an amount the instruction does not state, a veto window out of range, checked as `setMode` checks it), and a failed one saves nothing. A run already in its veto window was made by the old version, so autopilot holds it at the end of the window (`policy_changed`): it never pays under the old rule. **Every other edit waits for an approval**, as before: a proposer's, any edit with four eyes on, and an edit of a draft never approved (its first approval stays an explicit step after the preview). The policy goes back to draft (it stops running), autopilot is switched off, and the new version needs an approval; such an edit cannot switch autopilot on (`policy_not_approved`) and a veto window it names is ignored. The audit stream's `policy.edited` says which (`applied`, the resulting `mode`, `previousMode`, `autopilotOff`). `discard` of an edit restores the last approved version, paused; of a new draft, archives it.
5. **Run** (`SchedulerService.tick`, below) with no AI at runtime.
6. **Pause, resume, mode, veto window, archive, veto**: the current approver role only. Resuming never backfills the periods it missed.

### Schedules and periods

Weekly (weekday and time) or monthly (day and time) in an IANA timezone, UTC by default (`domain/policy/schedule.ts`). The time is an hour and a minute (0 to 59, 0 by default, so a schedule stored before minutes existed, with no `minute` in its JSON, reads as on the hour and runs exactly as before); every surface says it as HH:MM. **Daily** (a time) exists for the testnet demo only, so judges are paid with nobody online: `scheduleAllowed` lets it through only with the demo controls (`RolepayDeps.demoControls`, which counts only on Moderato, and config refuses the flag elsewhere). Without them `PolicyService` refuses to create, edit into, approve or resume a daily policy (`schedule_not_allowed`, before the model is called), lists it with no next run, and the scheduler never runs one or makes it with `runNow`. The schedule is an option of the command or form and never comes from the model: the criteria prompt says to leave a schedule in the instruction ("every day at 18:00 UTC") out, and the answer's schema has no schedule. A daily period is the day since the previous occurrence, keyed by its end like the others; daylight saving works the same way. Local times are turned into instants with the runtime's timezone database: a time that does not exist (the spring gap) runs as far past the gap's end as it was into it (with 02:00 to 03:00 skipped, 02:00 runs at 03:00, when the gap ends, and 02:30 at 03:30), and one that happens twice runs the first time. A day past the end of a short month runs on its last day. A run covers one period, from the previous occurrence to its own, at most 31 days back (the criteria bound); the compiled rule's counting windows are moved onto that period (`windowedCriteria`), everything else (roles, anchors, exclusions) stays as compiled. Only the latest occurrence after the policy became active is run: a server that was down for two weeks makes one run, not a backlog.

### Modes, the veto window and autopilot

- **propose** (the default): each run is created and submitted, then waits for the normal one-tap approval (the existing review embed).
- **autopilot** (an explicit switch by an approver on an approved policy): the run is posted with "pays at <time> unless vetoed" and a Veto button, and pays after the veto window (default 24 h, at least 1 h; a testnet server with the demo controls, `ROLEPAY_DEMO_CONTROLS=true`, allows 1 minute for demos and manual tests). The scheduler approves it in the name of the approver who switched autopilot on, through `PayRunService.approve`, then `execute`; the bot key's on-chain limit caps it like any run. Before approving it checks again, every time: the policy is still active, still on autopilot and at the version that made the run, the community's approver role is the one recorded when autopilot was switched on, and that person still holds it (one Get Guild Member through the ActivityReader). If any of these fail, autopilot stops: the run stays pending for the normal approval and the message says why. Nobody approves a run autopilot released, so its message never says "Approved by": it reads "Paid on autopilot after the veto window; no veto. Policy approved by @A (version N)." (plus who switched autopilot on, when that is someone else), wherever the run is shown (the notifier, the recovery sweep's report, Retry and its job, `/rolepay status run:`, the dashboard's run page). A run counts as released on autopilot when its policy run was released and the run was approved once the window was over (`releasedOnAutopilot`); a person who approved it during the window, or after autopilot stopped, is named as its approver.
- **The veto** (`PolicyService.veto`, the approver role, from the Veto button in Discord or the run's page on the dashboard): cancels the run, records who and when. It counts until the run is released: the release takes the run from `scheduled` by compare-and-set, the veto takes it the same way, and exactly one wins. The domain itself refuses a release before `executeAfter` (`movePolicyRun`), so no scheduler bug can pay early.

### Guardrails

- A cap per run (a run over it is held whole) and per person (each line is cut to it, overrides included, after the rule).
- A run that would exceed what the bot key has left, has no active key, or has more people than one run holds is **held whole and explained** (`runGuards`: the code and the numbers), never partly paid. What the key has left is compared with the most the run can take from it (`PayRunService.spendCap`, the same `payoutSpendCap` the pre-flight uses: a line paid in a preferred stablecoin at its maximum swap input), so a run that fits only without its swaps is held when it is made, as `swaps_over_budget` (`swaps_over_policy_budget` on a policy's own key), with that most as the total; the policy's cap per run stays on what people receive. A held run makes no pay run. At execution the usual pre-flight (`checkKeyForRun`) runs again: a key revoked or spent during the veto window holds the approved run (Retry in Discord), and the batch is atomic anyway.
- Revoking the key stops everything (no active key: held). Pausing stops new runs and autopilot releases.
- **A policy with its own key** is held against that key's remaining budget instead (`over_policy_budget`, `swaps_over_policy_budget`, `policy_key_inactive`), whatever the bot key has, and its runs are signed with that key only (Policy keys, above).
- The recovery sweep reconciles autopilot runs left executing like any run; the scheduler's own records survive restarts (below).

### One run per policy per period

- The scheduler claims a period by inserting the PolicyRun: the repository's unique key on (policy, period key) lets exactly one insert succeed, so a double tick, a restart or a second instance does nothing.
- The pay run's ID is chosen at the claim and stored with it (`PayRunService.create(input, { runId })`): if the process dies after the run exists but before the PolicyRun links it, whoever carries on finds that run and never makes a second one.
- Work in progress (`generating`, `releasing`) holds a lease (5 minutes); another instance takes it over only once it has run out. Every move is a compare-and-set on `rev`.
- Releasing calls `approve` and `execute`, both idempotent behind the run's own compare-and-set, so never-pay-twice holds as for any run.
- A period where nobody matched makes no pay run: the PolicyRun is `empty` (it still claims the period, so a restart or a second instance does nothing more) and the audit stream gets `policy_run.empty`. The notifier posts one line for a weekly or monthly policy and nothing for a daily one (`quietWhenEmpty`): the judge demo waits most days for someone new.

```
PolicyRun: generating --> proposed | scheduled | held | empty
           scheduled --> vetoed | releasing --> released | held | cancelled
```

### The audit stream

Every policy and run event, append-only (`AuditLog` port, `audit_events` table): `policy.created`, `compiled`, `edited`, `approved`, `discarded`, `paused`, `resumed`, `mode_changed`, `archived`; `policy_run.generated`, `held`, `empty`, `vetoed`, `released`, `cancelled`; and every pay run's `run.created`, `submitted`, `approved`, `cancelled`, `executing`, `paid`, `failed` (written by `PayRunService`, best effort so an audit outage never fails a payment step); and funding's `funding_source.created` (the approver who made it, the source ID and its deposit address) and `deposit.received` (Rolepay as the actor, the source ID, amount, token, transaction and log index; best effort, written only by the instance that stored the deposit); and `payee.address_changed` (a re-claim through a new link that moves someone's pay: the member as the actor, the old and new kind of address, `passkey` or `external`, and no address); and the treasury channel's `community.treasury_channel_chosen` (a Treasurer as the actor, the channel ID or null for none, and the one before) and `community.treasury_channel_found` (Rolepay as the actor, the channel named "treasury" it picked, and the channel it replaced when the one set was gone). Each event has the actor (the Discord user, or null for Rolepay itself), the time, the policy and version, the policy run and the pay run (a pay run made by a policy carries its policy), and details that are codes, amounts, counts and IDs, never anyone's words (instructions and names stay on their own records).

### Live updates (the live feed)

Every event the `AuditTrail` appends is also published, with its `seq`, to the `LiveFeed` port (`ports/liveFeed.ts`): the same points that write the audit stream, so nothing new can drift from it, and publishing never fails the write (a failure goes to `onAuditError`). A pay run event that could not be audited (best effort, above) is not published either. `LiveService` (`rolepay.live`) is what the web pages use:

- `community({ guildId }, listener)`: that community's events from now on, as `{ seq, at, type, communityId, runId, policyId, policyRunId }`, never the actor or the details; returns the unsubscribe;
- `since({ guildId, after })`: what a reconnecting page missed after its Last-Event-ID (the audit `seq`), oldest first, at most 50;
- `payments({ address }, listener)`: each run line paid to that address as its run is paid (amount, the token delivered, run, line, transaction, the community's name). One feed subscription serves every listening account: each `run.paid` reads its run once and hands each line only to the listeners of that line's address;
- `received({ address, limit })`: what an address was paid in the last year, newest first, across the communities it is registered in (`linesPaidTo` in `domain/received.ts`, pure).

`InProcessLiveFeed` (`adapters/live/`, opened by `openRolepayAdapters`) keeps its subscribers in memory: **one instance only**. With two server instances, a page connected to one sees only that instance's events (a payment made by the other appears on the next reconnect or reload). A shared bus (Postgres LISTEN/NOTIFY) can replace it behind the same port. Without a feed in the deps, `live.enabled` is false and subscribing does nothing.

## Funding with attribution (deposit addresses)

**Every funder gets its own address; the money lands in the treasury itself.** Tempo's T3 upgrade added virtual addresses for TIP-20 ([TIP-1022](https://tempo.xyz/developers/docs/protocol/tips/tip-1022), with Tempo's [guide](https://tempo.xyz/developers/docs/guide/payments/virtual-addresses) and [overview](https://tempo.xyz/developers/docs/protocol/tip20/virtual-addresses)). An account registers once as a *master* and gets a 4-byte masterId. Any address of the form `[masterId][fdfdfdfdfdfdfdfdfdfd][6-byte userTag]` is then a deposit address of that account: a TIP-20 transfer (or mint) to it is credited by the token precompile to the master, inside the same call, and the virtual address never holds a balance. There is no sweep transaction and no account state per address. Rolepay registers the treasury once and derives one deposit address per named funding source off chain ("Q4 bounty sponsor: Acme DAO", "Judges pool"). It is off by default: a community that never sets it up has no master, and the watcher reads nothing for it.

**Registration, on the treasury page, one passkey prompt.** The registry precompile (`0xfdc0...`) computes `keccak256(treasury || salt)` and accepts a salt only if the first 4 bytes are zero (a 32-bit proof of work, so nobody can cheaply land on someone else's masterId); bytes 4 to 8 are the masterId. The page:

1. mines the salt in the browser with viem's `VirtualMaster.mineSaltAsync` (WebAssembly keccak in Web Workers, all but one core: about 4.3 billion tries on average; Chromium on a 12-core laptop does about 42 million a second, so about a minute and a half on average, and the time varies a lot from one search to the next; the setup page alone allows `'wasm-unsafe-eval'` and `worker-src blob:` in its CSP for this, see packages/web). The demo machine is a shared CPU and could not mine in reasonable time without starving Discord's 3-second answers, so the server never mines. ox's browser workers (ox 0.14.45) set their message handler only after WebAssembly starts, and the page posts each one its start message at once, so a worker could drop it and never mine (in Chromium: no progress at all, or a fraction of the workers). `client/deposits.ts` puts a small queue in front of the worker's source (`WORKER_QUEUE_SHIM`, only while mining) and stops with "reload and try again" when no progress comes for 15 seconds, so the page never waits for ever. It also searches up to 2^40 salts: ox stops at 2^32 by default, which holds no valid salt for about 37% of accounts, and since each search starts from the same salt, such a treasury would fail on every try;
2. builds `registerVirtualMaster(salt)` itself (`buildRegistration` in `client/deposits.ts`) and asks the server to plan it (`POST /setup/:token/deposits/plan`: `FundingService.planMaster` checks the proof of work and that the masterId is free on chain, and answers with its copy of the call). The page compares the server's masterId, master, contract and calldata with its own and signs nothing if any differs (`registrationMismatch`), as it does for the key authorisation. A taken masterId (rare) means mining on from the next salt;
3. sends it with the treasury passkey, sponsored on testnet (viem's `Actions.virtualAddress.registerMasterSync`), and checks the masterId in the chain's `MasterRegistered` event;
4. `POST .../deposits/confirm`: `FundingService.confirmMaster` records the master only when the registry maps the masterId to the treasury (`getMaster`), never on the page's word, and starts the watcher at the registration's block (or at the head when the named transaction is not that registration: no deposit address exists before this, so nothing earlier can be missed). Registrations are permanent on chain (TIP-1022 has no rotation), so one master per community, recorded once.

**Funding sources.** The approver role creates them, from the dashboard's Funding page or `/rolepay fund new name:` (core re-checks the role, `canManageFunding`). Each takes the next user tag (1, 2, 3 as 6 bytes; a UNIQUE constraint on community and tag, so two instances creating at once each get their own) and its deposit address is `depositAddress(masterId, userTag)`, pure in `domain/funding.ts`. A name already in use is refused with that source (so Discord can show its address); at most 200 per community. The name is user text: it stays on the source and never reaches the audit stream or a log.

**Attribution, as TIP-1022 describes it.** A forwarded transfer emits two standard `Transfer` events in one transaction: `Transfer(sender, depositAddress, amount)`, then `Transfer(depositAddress, treasury, amount)` (with a `TransferWithMemo` between them for `transferWithMemo`, and `Mint` for a mint, whose sender is the zero address). `attributeDeposits` (pure) pairs each first hop to one of the community's deposit addresses with the next second hop in the same transaction from that address to the treasury, same token and amount, and records ONE deposit per pair, keyed by the first hop's transaction and log index. Counting both events would count every deposit twice. A pair whose sender is the treasury itself is self-forwarding (TIP-1022 says not to count it as inflow) and is left out; a first hop with no forward to the treasury is left out too. The record says where money arrived, not who signed for it: anyone can send to a deposit address, so the sender is stored beside it.

**The watcher** (`FundingService.scan`, the server's `startFundingWatcher`, every `ROLEPAY_FUNDING_INTERVAL_SECONDS`, 30 by default, on the same non-overlapping loop as the recovery sweep and the scheduler). With no master anywhere it makes no chain call. Otherwise it reads the head once, then for each master the blocks after its cursor (at most 10,000, about 100 minutes of Tempo blocks, so a server that was down catches up over a few ticks): two `eth_getLogs` per chunk on the payout token and the network's known USD stablecoins (`KNOWN_TOKENS`), one for first hops (`to` in the community's deposit addresses, 100 at a time) and one for second hops (`from` in them, `to` the treasury), block times from the logs' `blockTimestamp`. Each deposit is inserted if absent on (transaction, log index), and only the call that inserted it writes `deposit.received`, so a double tick, a restart, a rescan or a second instance on the same database stores and audits each deposit once. Then the cursor moves forward (never back). A range that cannot be read keeps its cursor and is read again next tick; other communities go on. Tempo blocks are final when produced, so there are no reorgs to undo.

**Reading it.** `funding.status` (the master and each source with what it received), `funding.deposits` (newest first, per source), `funding.month` (this UTC month: the total, per token, and from how many sources; `setUp` false hides the Overview card). All tokens watched are USD stablecoins with 6 decimals, so a mixed total is shown in USD with each token's part.

| Port | Methods | Implementations |
| --- | --- | --- |
| `FundingChain` (`ports/fundingChain.ts`, read only, separate from `PayoutChain`: nothing here touches the payment path) | `head`, `registration({ master, salt })` (masterId, proof of work, the call: computed, no RPC), `masterOf(masterId)`, `findRegistration(txHash)`, `forwardedTransfers({ tokens, addresses, master, fromBlock, toBlock })` | `TempoFundingChain` (viem's `Actions.virtualAddress` and `VirtualMaster`), `FakeFundingChain` (an in-memory registry and transfer log that emits the two hops; the proof of work is simulated) |
| `FundingRepository` (`ports/repositories.ts`) | `getMaster`, `insertMaster` (one per community), `listMasters`, `advanceScan` (forward only), `insertSource` (`tag_taken`), `getSource`, `listSources`, `insertDeposit` (true once), `listDeposits` | memory and SQLite, one contract (`test/support/fundingRepositoryContract.ts`) |

Proven on Moderato by `packages/core/test/funding.chain.test.ts`: a passkey-like treasury (a P256 key signing WebAuthn envelopes) mines a salt and registers; two deposit addresses each receive AlphaUSD from a faucet-funded account; the treasury's balance rises by exactly each amount in the deposit's own block, the deposit addresses hold nothing and the treasury sends nothing (no sweep), and the watcher attributes both deposits once. The browser half (mining under the setup page's CSP, the tampered plan refused, one passkey prompt) is `apps/server/e2e/depositAddresses.spec.ts`. The testnet faucet (`tempo_fundAddress`) also works on a deposit address: it mints 1,000,000 of each test stablecoin, forwarded to the treasury (three of the five are tokens Rolepay watches on Moderato).

## apps/server (Hono on Node)

The composition root (`src/main.ts`). It parses config (`src/config.ts`: the server's own `DISCORD_*`, `PUBLIC_URL` and `ROLEPAY_RP_ID`, `HOST`/`PORT` and bot-key defaults, plus core's `ROLEPAY_*` through `parseConfig`), opens the production adapters, creates the services and serves:

- `POST /discord/interactions`: the Discord interactions endpoint (HTTP interactions, no gateway bot).
- `GET /health`: `{ ok, network, jobsInFlight }`.
- `/`, `/claim/:token`, `/setup/:token`, `/account` (with `/account/received` and the stream `/account/live`), `/webauthn/*`, `/assets/rolepay.js`, `/assets/live.js`, `/assets/fonts/*`, `/favicon.svg`, `/apple-touch-icon.png`: the web pages (`@rolepay/web`, below).
- `/dashboard`, `/auth/discord`: the web dashboard (below). `src/dashboard.ts` wires it: the bot's REST client as the member view and as the channel view (`restGuildChannels`: the text channels and the confirmation of the treasury channel), Discord OAuth2 when `ROLEPAY_DISCORD_CLIENT_SECRET` is set, and the policy seam (`src/policySeam.ts`, below), whose vetoes `compose.ts` also announces in Discord. `compose.ts` shares one `RunNotices` between the interactions, the executor, the notifier and the recovery sweep, and logs a `treasury_channel` line (channel IDs and codes only) when Rolepay finds #treasury or cannot post in the treasury channel.
- The recovery sweep: `payRuns.recoverInFlight()` on start and every 30 seconds (`src/recovery.ts`), never two at once, skipping runs with a job in this process. Runs it settles are reported in Discord as part of the sweep (`createRecoveryNotifier`).
- The policy scheduler: `scheduler.tick()` on start and every `ROLEPAY_SCHEDULER_INTERVAL_SECONDS` (30 by default; 10 on the demo, `fly.demo.toml`, so a one-minute veto window pays soon after it ends) on the same non-overlapping loop (`src/scheduler.ts`), then `createPolicyNotifier` posts what it did. A second instance on the same database is safe (one run per policy per period, compare-and-set releases).
- The deposit watcher: `funding.scan()` on start and every `ROLEPAY_FUNDING_INTERVAL_SECONDS` (30 by default), the same loop (`src/funding.ts`), with a `funding` log line (source IDs, amounts, tokens, transactions; never a source's name) when it found something. Safe with a second instance (see Funding with attribution).

**The passkey domain is config only.** `PUBLIC_URL` is the public origin (the tunnel URL while developing); the WebAuthn rpId defaults to its host, or `ROLEPAY_RP_ID` names a parent domain. Config refuses what browsers refuse for passkeys: plain http off localhost, an IP address, a path, an rpId that is not the host or a parent of it; on mainnet it also refuses anything but https (a treasury passkey made on localhost would only ever work there). Moving to the production domain means changing these two values, and passkeys made on the old host do not carry over. The hosts are `https://demo.rolepay.app` (the testnet demo, `fly.demo.toml`) and `https://web.rolepay.app` (mainnet, `fly.app.toml`, runbook `apps/server/MAINNET.md`), two servers with their own config and database.

**Guards at the edge.** At start the server asks the RPC for its chain ID and refuses to start when it is not the configured network's (a mainnet server behind a testnet RPC, or the reverse); an RPC that does not answer only gets a `chain_check_failed` log line. Every request body over 1 MB is refused with 413 before anything reads it (`MAX_BODY_BYTES` in `compose.ts`, counted as it arrives when there is no Content-Length). `POST /discord/interactions` has a budget for junk only (`defaultInteractionLimit` in `compose.ts`): per client (the client key the web limits use), a burst of 10 requests that FAIL the Ed25519 signature check, then one every 5 seconds. A request that passes the check never takes from it, because Discord sends every server's interactions from the same few addresses; there is no overall budget, which junk from many addresses could spend for Discord too; and a request with no client address (no proxy in front) is never limited, since all of those would share one budget. A client over its budget is answered 429 (`retry-after: 5`) before its body is read or a signature is checked. The start log line names the network, the chain ID, the payout token and who pays fees.

**Production runs compiled JavaScript.** `pnpm build` (`scripts/build.ts`, esbuild) writes `dist/main.js`, the server with the workspace packages' TypeScript compiled in and every npm package left as an import (so better-sqlite3's native addon loads as usual; those packages are the server's own dependencies for that reason), and `dist/rolepay.js`, the client bundle. The image runs `node dist/main.js`: nothing is transpiled at runtime and no page request waits for esbuild. `pnpm dev` still runs the sources with tsx and builds the client bundle on first request.

`composeServer` (`src/compose.ts`) is the wiring shared by `main.ts` and the tests: the tests pass in-memory adapters, a fake Discord and fake passkey sessions and drive the real Hono app over HTTP; the Playwright e2e passes the production set with real passkeys. **The look.** One design language on every page: dark only (`color-scheme: dark`), a fixed near-black ink ground with a faint gold light and a grain overlay (CSS pseudo-elements, the grain a `data:` SVG), content in panels separated by a hairline of light rather than boxes, small uppercase labels, Lora for headings and headline numbers, Montserrat for everything else. Gold (`#EDBE5A`, the mark's) is kept for the primary button, the focus ring and the current page; status colours appear only in small marks (pills, dots, diff lines). `views/theme.ts` holds the shared base, the mark (inline in every header and served as `/favicon.svg`; `appleTouchIcon.ts` holds it as a 180 by 180 PNG with no alpha channel, served as `/apple-touch-icon.png` for the iPhone home screen, inline so the production bundle carries it, and covered by `img-src 'self'`) and the head tags; each of the two stylesheets (`STYLE` for the pages, `DASHBOARD_STYLE` for the dashboard) starts with it and stays one inline `<style>` allowed by its hash. The fonts are served from this origin (`font-src 'self'`), so nothing on any page loads from another site. In production they resolve from `apps/server/node_modules`, which is why the server depends on the font packages too (`apps/server/test/runtimeDependencies.test.ts`). Every text colour passes WCAG AA on the lightest surface (the contrast figures are in `theme.ts`). Phones first: 16px gutters, tables scroll inside their own wrapper, inputs at 16px so iOS does not zoom.

**Why server-rendered HTML plus one client bundle**, not a separate `apps/web` with Vite: the pages are two forms, and passkeys bind to one origin, so the pages, the WebAuthn endpoints and the API must be served together anyway. Vite would add a second dev server and a proxy for the same result. esbuild is already installed (through tsx), bundles the Accounts SDK and viem for the browser in about a second, and `pnpm dev` keeps working with no build step (production builds the bundle once, with the server: `pnpm build`). The bundle is about 1.5 MB (mostly viem's Tempo ABIs), served gzipped. A framework can come later behind the same routes if the pages grow.

**Passkeys.** The browser uses the Tempo Accounts SDK's `webAuthn` adapter (`Provider.create({ adapter: webAuthn({ auth: '/webauthn' }) })`) and `wallet_connect` to register or sign in. The ceremonies run against `Handler.webAuthn` on this server, which checks the origin and rpId from config, stores each credential's public key (WebAuthn sign-in does not return it, so returning users need the server to remember it) and issues a session cookie. The store is core's KeyValueStore, so credentials survive restarts and move to Postgres with the rest. The server derives the Tempo address from the session's public key; a page never tells the server an address. **One passkey name per person.** Asked to register a name this browser already remembers, the SDK signs in to that account instead of creating one, so a name must belong to one person: a payee's passkey is `Rolepay: <community> (<Discord username>)` (the Discord ID for a link that kept no username; `passkeyNames.ts`, at most 64 bytes, the community name shortened first) and the treasury's `Rolepay treasury: <community>`. Two payees of one community claiming in one browser (a shared device) get two passkeys; the same payee claiming again is signed back in to their own. Until 2026-10-08 a payee's name was the community's alone, and the second person was registered at the first person's address (`client/passkey.test.ts`, `apps/server/e2e/passkeys.spec.ts`). A browser can remember a passkey account the server no longer knows (its database was reset): the SDK then signs in with it when asked to create a passkey of the same name, and the server answers "Unknown credential". `client/passkey.ts` forgets those remembered accounts through the SDK's store and storage and registers once more, and the page says in plain words when a passkey is unknown (`client/passkey.test.ts`, on the real SDK Provider with the ceremonies faked; `apps/server/e2e/passkeys.spec.ts` in a real browser, the server's credential deleted as a reset would). A remembered account still signs and shows its balance without the server, so it is kept on page load.

**Claim.** `GET /claim/:token` describes the link and offers two choices, "Create my passkey (no wallet needed)" first and "Use a wallet I already have" second; `POST /claim/:token` with a passkey session registers that session's address (`payees.register`, which consumes the link once).

**A wallet they already have** (`POST /claim/:token/wallet/challenge`, `POST /claim/:token/wallet`; `domain/walletClaim.ts`, `PayeeService.walletChallenge` and `registerExternal`, `client/wallet.ts`). The page talks to the injected EIP-1193 wallet (`window.ethereum`, for example MetaMask) from the same bundle, so nothing loads from another site and the CSP is unchanged. It asks for the account, switches the wallet to the network's Tempo chain from viem's definition (`wallet_addEthereumChain` the first time, with the native currency as USD at 18 decimals, which MetaMask requires; Tempo has none), checks it is there, and reads the selected account. The challenge stores a fresh nonce on the claim link (replacing any before it) and returns the message, built by the server from its own configured origin (never the request's Host) and chain:

```
Rolepay on web.rolepay.app: pay me in <community> at <address> on Tempo (chain 4217).

Discord user: <username> (<Discord ID>)
Origin: https://web.rolepay.app
Claim nonce: <nonce>
Issued at: <ISO time>

Signing proves this address is yours. It costs nothing and moves no money.
```

The wallet signs it with `personal_sign` (EIP-191) and the page posts the message and the signature. `registerExternal` accepts only the exact text `walletClaimMessage` builds (`parseWalletClaimMessage` rebuilds and compares), takes the link's nonce on the first attempt that names it (a compare-and-set, `takeLinkNonce`, so each nonce is tried once whatever comes next: `nonce_mismatch` for a made-up, replaced or used one), refuses one issued ten minutes ago or more (`nonce_expired`), another origin (`wrong_origin`), chain (`wrong_chain`), community or member (`message_mismatch`), recovers the signer through the `MessageSignatures` port (`ViemMessageSignatures`: viem's `recoverMessageAddress`, secp256k1, offline), and registers that address as `external` only when it is the address the message names (`signature_mismatch` otherwise). A signature that is not 65 bytes of hex is `malformed_signature`; a longer one (a smart-contract account's ERC-1271 or ERC-6492, a Tempo passkey, P256 or access-key envelope) is `unsupported_signature`, and the page says "This wallet's signature type isn't supported yet; use a passkey." A person who declines in the wallet (EIP-1193 4001) reads a calm sentence, not an error. Success says "You will be paid at <address>. Keep that wallet: Rolepay cannot move or recover money there."

Everything downstream reads the stored address and nothing else: runs, policies, preferred stablecoins (chosen with `/payee prefer`, since there is no passkey session for the claim or account page to use) and the never-paid filter work unchanged; `packages/core/test/externalAddress.chain.test.ts` registers a fresh EOA this way on Moderato and a real run pays it, the line found by its memo. The DM receipt's "Your account" opens the address on the explorer for an own wallet (and for an address the payee has since moved from), the account page for a passkey account (`sendReceipts`). The dashboard marks own wallets on the Payees page. A re-claim through a new link may switch between kinds; one that moves someone's pay is audited as `payee.address_changed` with the old and new kind only. What the signature proves, and what it does not, is T34 in the threat model.

**Preferred stablecoins.** The claim page offers the community's choices once the passkey registers; the account page lists every community that pays the signed-in passkey (`GET /account/payouts`) with a choice each. Its balances follow: every coin a community pays the account in and every coin it chose, at 0 too, a chosen one marked "preferred" and listed first, then any other coin it holds (`coinsToList` in `client/payouts.ts`); a saved choice moves the rows at once, without reading the chain again. Both save through `POST /account/preference` (`{ guildId, token }`), which takes the address from the verified passkey session, never from the page, and is rate limited like the other public POSTs. The setup page has the treasurer's switch (`POST /setup/:token/preferred-tokens`, the treasury passkey only) and, with it on, builds the key authorisation with the swap scope itself (`buildAuthorization` with the page config's `swapTokens`, in core's order), still refusing a server copy that differs.

**Account.** A payee's passkey is bound to this server's host, so no other wallet can sign for their account: without a page here, money paid on mainnet could not be moved. `GET /account` is that page, the same for everyone: the browser signs in with the passkey (or uses the account it remembers, with no prompt), reads the balances of the network's known stablecoins (`KNOWN_TOKENS`) from the chain, and sends a plain TIP-20 `transfer` with one passkey prompt straight to Tempo (`client/account.ts`, `sendToken` in `client/tempo.ts`): sponsored on testnet, otherwise its fee comes out of the token sent and Max keeps 0.1 for it. There is no server endpoint for it, so the server never takes an address or an amount. `client/send.ts` refuses a malformed address, the account itself, the zero address and token contracts (the TIP-20 prefix, which the protocol refuses too), and any amount over what can be sent, in words. The claim page and every receipt DM link it. It works for any passkey account on this host, the treasury included, which is how a treasurer takes money back out of the treasury.

**Live pages (server-sent events).** Two streams, each authenticated and scoped exactly like the page it serves, over `rolepay.live` (the live feed above):

- `GET /dashboard/:guildId/live` (`dashboard/routes/live.ts`): a signed-in session whose member the bot sees in that guild, read fresh at connect as for an action (`communityAccess` with `fresh`), the same 401 and 403 as the pages; then that community's events only, as `event: audit` with `id:` the audit `seq` and data `{ seq, type, runId, policyId, policyRunId }`. A `Last-Event-ID` replays what was missed (at most 50).
- `GET /account/live` (`routes/accountLive.ts`): a passkey session; then `event: payment` for each run line paid to the session's own address, never an address the page sends, and nothing about anyone else. `GET /account/received` renders the account's Received list on the server for the same address.

Mechanics (`live/streams.ts`): `text/event-stream`, `retry: 5000` first, a comment line every 20 s (Fly's proxy closes idle connections), and at each heartbeat the route checks the stream may go on (the dashboard session still exists and the bot still sees the member, through the minute-long member cache; the passkey session is still the same address), closing it otherwise. Open streams are capped per signed-in person or passkey session (6) and per client address (30, keyed like the rate limits), answering 429 `too_many_streams` over that, and each connection takes from a `live` token bucket (`rateLimitGroup`). Closing for any reason (the browser leaves, a heartbeat check fails) unsubscribes from the feed and frees the slot, once. EventSource is same-origin, so `connect-src 'self'` already covers it: the CSP is unchanged.

The browser side is progressive enhancement. A community's dashboard pages carry their stream on `<body data-live>` and mark what changes with `data-live-region` (the Overview's At a glance, its cards and recent runs; a run's status, facts and timeline, with `data-live-run` so that page reacts only to its own run; the Runs list; the Audit log and its AI proposals; Funding's month, sources and deposits; a policy's Latest run). Regions never wrap a form someone may be typing in (filters, a new source's name). An autopilot run's veto window is `<span data-countdown>` ("pays at <time> unless vetoed" without JavaScript); the script counts it down each second ("pays in 0:42 unless vetoed") and re-reads the page when it runs out, so the run flips to paid or vetoed as the scheduler releases it. On an event, `/assets/live.js` (`client/dashboardLive.ts`) re-reads the same URL with the same session and swaps the marked regions' HTML in from the fresh copy (a burst of events, such as approved, executing and paid, becomes one re-read; after a reconnect it re-reads once; on a 401 or 403 it stops). So all rendering and escaping stays on the server and there is one renderer per page. The account page (`client/account.ts`) follows `/account/live` once the server knows its passkey: it re-reads `/account/received` (new rows slide in) and reads the token's balance from the chain through the existing RPC client, read again a few times if the RPC answers behind the event, then counts up from the old value over about a second with a gold glow; with `prefers-reduced-motion` it just shows the new value.

**Setup.** `GET /setup/:token` (page), `GET /setup/:token/state` (community, key and chain state, who is signed in), `POST .../treasury` (bind the signed-in passkey as the treasury, registering the community the first time), `POST .../key` (provision a key with the chosen limit, period, expiry and fee budget; returns the authorisation), `POST .../key/confirm` and `POST .../key/revoked` (read the result from the chain), and for deposit addresses `POST .../deposits/plan` and `POST .../deposits/confirm` (see Funding with attribution). Everything after binding needs the session of the passkey that is the treasury, and the session must prove that passkey: one minted by `/webauthn/login` (an assertion, a signature over a server challenge with the stored public key; `withLoginProof` records it, by token hash), or the registration session that created the treasury (issued before the community existed). Any other registration session is refused with `sign_in_required`, because a registration with attestation "none" carries no signature: anyone could register the treasury's public key, which is public on chain once it signs, and get a session with its address. This keeps one prompt for creating the treasury and one for authorising the key right after.

**The page signs what the treasurer typed, not what the server says.** The WebAuthn prompt shows no transaction details, so the page builds the key authorisation itself (`buildAuthorization` in `client/keychain.ts`): the limit and period from the form, an expiry from the device clock ("expires after N days", sent to the server as `expiresAt` so both hold the same number), and one call scope, `transferWithMemo` on the payout token from the page config (plus the fee budget limit in fee_budget mode). It shows those exact values in plain words above the button, sends the form to `POST .../key`, takes only the key address from the answer, and refuses to sign (`authorizationMismatch`: "Nothing was signed") if the server's copy differs in any limit, period, expiry, target, selector or recipient. The Playwright e2e tampers the answer in the browser and checks that no passkey prompt happens. Caveat for the trust model: the page's JavaScript and config come from the same server that holds the bot key, so a fully compromised server could serve a different page. Accepted for the small mainnet pilot, where the loss is bounded by the treasury (tens of dollars); on the roadmap: serve the setup page as an immutable bundle from a separate static origin the bot server cannot change. The account page has the same caveat for a payee's passkey (bounded by what they were paid), and the same fix.

**A policy's own budget** (`/setup/:token/policies/:policyId`, `routes/policyBudget.ts`, `client/policyBudget.ts`) is the same page for one policy, behind the same gate (`treasurerOf` in `routes/treasurer.ts`: a live setup link for a bound community and the session of the passkey that is its treasury, proven by a sign-in) and with the same safety model: the form starts from the policy's cap per run and one run of its schedule (`policyKeyDefaults`; a monthly policy resets every 28 days, so no period of the key can hold two of its runs), the page builds the authorisation with `buildAuthorization` (with the swap scope for the page config's `swapTokens` while the state says preferred stablecoins are on, and a line in the budget status while this policy's key lacks it: `keyNeedsSwapScope`), shows it ("You will sign, for this policy only: ..."), takes only the key address from `POST .../key`, refuses to sign on any difference (`authorizationMismatch`), and signs with one passkey prompt. Its state lists only this policy's keys, so a replacement revokes this policy's live key and never the bot key or another policy's; and the setup page's own list never shows a policy key, so replacing the bot key never revokes one. `client/policyBudget.test.ts` runs the browser code on a fake DOM (the tamper refusal: no prompt, nothing confirmed); `apps/server/e2e/policyBudget.spec.ts` does it with a real passkey on Moderato.

The browser itself signs the keychain transactions (`client/tempo.ts`, with the passkey account, sponsored through the public sponsor on testnet; without a sponsor the treasury pays its own fee, in its fee token while it holds 0.1 or more, else in the payout token). On testnet a faucet button funds the treasury; in fee budget mode the funding step also asks for a little of the fee token and shows its balance.

**One passkey prompt per action.** Creating the treasury is one prompt (the new passkey), authorising the key is one, replacing it (revoke the old key and authorise the new one, in one transaction) is one, revoking it is one. The authorisation is a transaction from the root calling the keychain's `authorizeKey(keyId, signatureType, KeyRestrictions)` directly (`client/keychain.ts`), which a root key may do. viem's `accessKey.authorize` would instead sign a key authorization and then the transaction carrying it, two prompts for the same result on chain (the protocol runs the same `authorizeKey` for a signed key authorization). Revocation is viem's `accessKey.revokeSync`, already one transaction. The only second prompt is a sign-in: when the treasury's server session is live but this browser no longer remembers the passkey account (site data cleared), the page must sign in before it can sign, and says "Your device will ask twice" before the click. The Playwright e2e counts every WebAuthn call to hold these numbers, and reads the key's call scope back from the chain.

Layering is enforced by `packages/web/test/architecture.test.ts`: server code imports only `@rolepay/core`, hono, zod, the Accounts SDK server, `viem/tempo`, esbuild and node; client code imports only the Accounts SDK and viem; views (the dashboard's too) are pure; nothing imports the fakes.

## The web dashboard (`packages/web/src/dashboard/`)

Per community: Overview, Runs, Payees, Policies, Funding and the Audit log, read only for members, with actions for the approver (Treasurer) role. The AI spend is read only for everyone: the Overview's "AI this month" card (the estimated total, the calls, the average cost of a drafted proposal), the Audit log's "AI proposals" (the latest 50 that reached the model: who asked, the mode, the model, the latency, the cost, the outcome and the run it became) and, on a policy's version history, what compiling each version cost. It lives in `packages/web` because it shares the origin, the security headers (CSP, HSTS, no framing), the rate limits and the same-origin check with the claim and setup pages. Every page works without JavaScript (forms post and redirect back, `<details>` expands). With it, a community's pages update live (below): one small script from this origin, `/assets/live.js` (a few kilobytes, no viem), so the CSP only adds its stylesheet's hash.

**At a glance.** The Overview leads with one panel: the bot key's budget this period as a bar, the spent part against the limit, the limit a hard end line (the trust model in one picture: the chain refuses any payment past it), with what is spent and left in the payout token, when the period resets and when the key expires; a revoked, expired, unauthorised or missing key is said in words and no bar is drawn. Beside it (below it on a phone), paid per week for the last 12 UTC weeks (Monday start, the current week labelled "so far"), a policy's runs apart from runs made by hand, with the 12-week total, a legend and "Show the numbers" (a table with every value). Both are inline SVG from pure builders (`views/charts.ts`): no script, no chart library, no style attribute (classes in `DASHBOARD_STYLE`), each an image whose label summarises it, with native tooltips per week. Sizes are percentages of the width rather than a scaled viewBox, and there is a wide and a narrow drawing of the weekly chart, one shown at a time by a media query, so text keeps its size on a phone. The budget reads the same key state as the Bot key card (no extra chain call); the weeks come through `PayoutsPort`.

**Sign-in with Discord.** OAuth2 authorization code with PKCE (S256) and state, scopes `identify guilds`, the client ID is the app ID and the secret is `ROLEPAY_DISCORD_CLIENT_SECRET` (unset: every page says sign-in is not configured). `/auth/discord` keeps the PKCE verifier and where to return under a hash of a fresh state for ten minutes and puts the state in an HttpOnly cookie. The callback requires the query's state to equal this browser's cookie (otherwise anyone could send a victim a callback link and sign them into the attacker's account), takes the pending sign-in once, exchanges the code with the verifier, reads the user and their guilds and revokes the token: Rolepay keeps no Discord token. It then mints a new session, never one the browser brought (no session fixation; a session the browser carried is ended), kept in the KeyValueStore under a SHA-256 of its random token for eight hours with its own CSRF token. `next` only returns to a `/dashboard` page on this origin. Sign out is a POST with the CSRF token and deletes the session on the server.

**Authorisation.** Roles come only from the bot's view of the member (Get Guild Member as the bot, no privileged intent), never from the browser or the sign-in snapshot; the guild list from sign-in only builds the home page. A page needs the guild to use Rolepay and the bot to see the person in it, with the same 403 for both, so a page reveals neither; that read is cached a minute. An action (`actionAccess`) needs the session's CSRF token, re-reads the member fresh (a role removed in Discord stops the next click), needs the approver role, and hands the services the actor's roles so they check again. A form field claiming roles is ignored.

**Referrer-Policy.** The site sends `no-referrer`, under which a browser sends `Origin: null` on a form post, and the same-origin check refuses it. Dashboard responses send `same-origin` instead (still nothing to other sites). The browser e2e found this; the in-process tests could not.

**Reads.** Only core services (`communities.get`, `keyStatus`, `treasuryBalance`; `payRuns.list`, `get`, `exportCsv`; `payees.list`) and the ports. Chain reads (balance, key) give up after 5 seconds and show "could not read the chain" rather than holding the page. The Runs and Payees pages read at most 1,000 runs and filter, page and total them in memory, which is fine at this scale (a repository query can replace it behind the same page). People are named through the bot (at most 60 lookups a page, cached ten minutes); anyone else shows their Discord ID. Every string a person or Discord controls is escaped, tested with hostile names, notes, policy texts and summaries on every page. Run details show what a run already stores; no Discord message text appears anywhere.

**Editing a policy in place.** A policy's page carries its editor for the Treasurer role: a `<details>` disclosure in the rule's panel with the new-policy fields, pre-filled from the newest version (no script). The words under the form say beforehand what saving does, as core decides it: on a policy approved before, with no separate approver required, the change applies as soon as it is saved, and the editor also offers the mode (propose or autopilot, and the veto window in minutes, pre-filled), with **Save and apply**; otherwise (a draft, or four eyes on) the new version waits for approval (another Treasurer's, with four eyes) and the policy does not run until then, with **Recompile and preview** and no mode. Saving posts to `/dashboard/:guildId/policies/:policyId/edit` and comes back to the same page: "Saved. Version N is in force." (`done=applied`) or the version waiting for approval (`done=edited`); a refused edit (a value the form or core refuses, nothing saved) re-renders the page with the editor open, the values sent and why. The old `GET .../edit` redirects to `?edit=1#editor`, which opens it. In both the new and the edit form, the stylesheet shows only the schedule fields the chosen kind uses (`form:has(select[name=kind] option[value=...]:checked)`), and the editor its veto window only with autopilot chosen; the server reads only those (`draftFrom`, `modeFrom`), so a hidden field's stale value is neither used nor refused. While the policy's latest run waits in its veto window but was made by an earlier version, its Latest run says autopilot will not pay it instead of counting down.

**The treasury channel.** The Overview has a "Treasury channel" panel, outside the live regions (a choice being made is never swapped away): the channel (by name, and whether a Treasurer chose it or Rolepay found it by its name), what goes there (everything only a Treasurer can act on: policies and runs to approve, runs you can veto, runs it holds, with their buttons; the channel each would have gone to gets a copy without them), and that it should be visible only to the Treasurer role and Rolepay, set in Discord. For the Treasurer role it is a form: a select of the server's text channels (`GuildChannels`, read as the bot with a 5-second limit, each marked when @everyone can see it), with "None: post in each policy's own channel". Saving posts to `/dashboard/:guildId/treasury-channel`, gated like every action: the choice must be one of this server's text channels as the bot reads them now (never an ID the form made up), Rolepay posts its confirmation there first and saves nothing if Discord refuses ("Rolepay could not post in that channel, so nothing was saved. Add Rolepay to the channel, with permission to send messages."), then `communities.setTreasuryChannel`; a channel @everyone can see is saved with a warning, which stays on the panel until the channel is private (the @everyone role's permissions, its ID being the server's, with the channel's overwrite for that role applied). While nobody has chosen, a Treasurer opening the Overview runs the same lookup by name as Discord's side (and posts the same confirmation); if there is no channel to find, the Overview asks, above its panels and on the setting: "Rolepay posts what needs a Treasurer in a channel of its own. Create a private #treasury channel, or choose one:". Members see the setting read only, and their visits read nothing from Discord for it.

**Funding.** `/dashboard/:guildId/funding` reads `rolepay.funding` directly (status, this month, the latest 100 deposits): this month's total and sources, where deposits land and the masterId, each source with what it received, its full deposit address (TIP-1022 asks UIs to show the whole address) and a QR code, and every deposit with its sender and transaction. The Treasurer role creates a source there (`POST .../funding/sources`, gated like every action). The QR code is an inline SVG from a pure builder (`views/qr.ts`: byte mode, error correction M, versions 1 to 6), so it needs no script; it is pinned by the published Reed-Solomon example, the format-bit table and a matrix that macOS CoreImage decoded back, for every version. The Overview's "Funded this month" card (what came in this UTC month, from how many sources) appears only once deposit addresses are set up.

### The policy seam

The Policies and Audit pages, the next scheduled runs on the Overview and the "made by a policy" part of a run (with its Veto button) read and act through two ports in `dashboard/policyPort.ts`; the AI spend is read through a third there, `AiUsagePort`, and what was paid each week (a policy's runs apart from runs made by hand, which is policy knowledge) through a fourth, `PayoutsPort`. `packages/web` never imports core's policy services: the port's types stay plain (Dates, bigint micro-units, a JSON-safe filter, words written by code), and the pages are tested without the AI or Discord.

Expected failures are results with snake_case codes. Core's state codes (`policy_not_draft`, `policy_not_active`, `policy_not_paused`, `policy_archived`, `not_scheduled`) arrive as `illegal_state`; a refusal while compiling (no model, AI off, the model declined, an unclear rule) as `could_not_compile` with the reason in words; the rest keep core's code (`not_permitted`, `version_mismatch`, `policy_blocked`, `creator_cannot_approve`, `invalid_veto_window`, `policy_not_approved`, `too_late`, ...), and the pages say each in words.

**One behaviour, two implementations, one contract.** `InMemoryPolicies` (`@rolepay/web/testing`) implements both ports the way core behaves: an edit of an approved policy is in force at once (only the approver role acts on the dashboard), and with four eyes on (`setSeparateApprover`) or on a draft it puts the policy back to draft until approved (it stops running, autopilot goes off), discarding an edit restores the last approved version paused, autopilot needs an approved policy, every action is audited. The page tests for Policies, a policy, the policy actions and the create flow, a run made by a policy and its veto, and the Audit log and its CSV are a contract (`policyPagesContract`, exported as `@rolepay/web/contract`) asserting against what each backend's own ports answer: `packages/web` runs it against `InMemoryPolicies`, `apps/server/test/dashboardContract.test.ts` against core on memory adapters through the adapters above. A backend says how it reaches each state (`PolicyBackend`: the Monday rule with a capped, an unregistered and a near-miss person, an unreadable channel, a spent key, an autopilot run in its window, a run Rolepay released, a community that requires a separate approver).

**A veto on the dashboard reaches Discord.** The run's message there says "pays at ... unless vetoed" with a Veto button; `vetoesAnnounced` (`compose.ts`) wraps the dashboard's policy port so a successful veto is announced to `createPolicyNotifier` as a cancelled run, and the message turns into "Vetoed by" without buttons, as when the button is pressed in Discord (both messages, with a treasury channel).

**So does a change to a policy whose preview is in the treasury channel.** `policyChangesShown` (`compose.ts`) wraps the same port: a successful approval, discard, edit or archive calls `updatePolicyMessages` (`@rolepay/discord`), which updates both messages of that policy's preview, if `/rolepay policy new` posted it with a treasury channel: "Active. Approved by" with when, "Discarded by", "Version 1 was replaced by version 2, edited by", or archived, never with buttons. A preview posted without a treasury channel is the command's own answer, which Rolepay cannot find again, so it changes only when its own buttons are pressed, as before.

## packages/discord

The Discord adapter. It calls core only through `@rolepay/core` services; everything external is a port with an in-memory fake (`@rolepay/discord/testing`).

```
http/        Ed25519 verification (WebCrypto) and the endpoint as a fetch handler: Request in, Response out; each interaction ID is answered once (InteractionLog), so a replay inside the 5-minute window gets 409
app/         Zod parsing of interactions, the router, permission rules, outcome rendering
commands/    slash command definitions (JSON) and handlers
components/  the Approve, Cancel and Retry buttons
views/       pure builders from domain objects to Discord message payloads
execution/   the in-process ExecutionQueue and the run executor job
adapters/    DiscordRest over fetch, MemberDirectory and core's ActivityReader over DiscordRest, KV stores
wire.ts      Zod schemas for Discord messages (message-command targets, history) and core's SourceMessage
ports.ts     DiscordRest, ExecutionQueue, MemberDirectory, RunNotices, InteractionLog, PendingSources
app/treasury.ts  the treasury channel: reading the server's text channels, the lookup by name, posting and updating the two messages of a run or a policy preview
```

A handler is a thin route: parse options with Zod, check permissions, call a service, return an **outcome** (`reply`, `update`, `defer` or `choices`). Handlers never talk to Discord; `app/outcome.ts` renders the outcome. A `defer` answers at once ("thinking...", or a `placeholder` that says what is happening, such as "Drafting a proposal…") and finishes in the background, then edits the reply through the interaction webhook; a public deferral that fails is deleted and the error goes to the caller alone. **The 3-second rule is enforced in the router**, whatever a handler waits on: one not done within 1.5 seconds (`ACK_DEADLINE_MS`) is acknowledged with a deferred response (a deferred update for a button or a form a button opened, a private "thinking..." for a command) and its answer is delivered by an edit or a follow-up when it is ready. A form ready that late cannot be shown, so the caller is asked to try again; autocomplete answers with no choices. Every request logs one `interaction` line: kind, command or component name, milliseconds until the response, `sinceCreatedMs` (from Discord creating the interaction, the time inside its ID, to the request reaching the server), its type, ok, late; never options, IDs or text. Work done after the answer (a deferral, a late answer) logs one `deferred` line as it ends: milliseconds after the response and its `phases` (`work`, `reply` to Discord, and the handler's own, such as `db` and `discord` for `/rolepay new`). Every response a button can get is checked against Discord's documented limits in `test/responseLimits.test.ts`. Layering is enforced by `packages/discord/test/architecture.test.ts`: discord imports only `@rolepay/core` and `zod`; views import nothing with IO; handlers never reach adapters, the HTTP layer or the queue implementation.

Decisions worth knowing:

- **Recipients.** `/rolepay new amount:<per person>` takes `role:` (every registered payee holding it), `users:` (mentions or IDs, `@bob=40` overrides the amount for one person), or both. Only registered payees can hold a line, so role filtering checks each registered payee with Get Guild Member, which needs **no privileged intent**. A List Guild Members implementation (which needs the GUILD_MEMBERS intent) can replace it behind the `MemberDirectory` port if a server ever has more payees than that is comfortable for.
- **Submit at create.** `/rolepay new` creates and submits in one go, so a run shown for review is `pending_approval`. Approve is one transition.
- **Approve answers with UPDATE_MESSAGE.** The review turns into "Approved, paying..." with no buttons inside the 3-second window (so nobody can click twice), the job is queued, and the job edits that same message with the result. A deferred update would leave the buttons live until the job finishes.
- **Subcommand groups.** `/rolepay policy new` arrives as command `rolepay`, sub `policy new`; the router keys handlers on `rolepay policy new`. A policy's messages are posted as the bot with `postMessage`, which returns the message ID, so the executor, the recovery sweep and the policy notifier all edit the same message (`RunNotices`).
- **Permissions** are checked from the signed interaction (`member.roles`, `member.permissions`), never trusted from `default_member_permissions` alone, which only hides `/rolepay` from non-admins by default (admins can grant it to the Treasurer role in Server Settings > Integrations). Manage Server alone cannot approve, and cannot change who approves: that takes the current approver role.

### The treasury channel

Discord shows a channel message's buttons to everyone who can read the channel, so a run posted in a public channel (#payouts) with Veto or Approve and pay offered those buttons to payees, who were refused when they pressed them. A community can therefore have a **treasury channel**: everything only a Treasurer can act on goes there with its buttons, and the channel it would have gone to gets the same message without them.

- **What goes there** (`app/treasury.ts`, shared by the policy notifier, the executor, the recovery sweep, the commands and the dashboard's policy actions): a policy's run waiting for approval (Approve and pay, Cancel) or in its veto window (Veto), a run held whole (the notice, posted in both channels since it has no buttons), a run made from Discord that waits for approval (`/rolepay new`, the pay form (Pay the author, Pay with Rolepay) and Create pay run on a proposal), and the preview of a policy written with `/rolepay policy new` (Approve policy, Discard). For those four, Rolepay posts the message with the buttons in the treasury channel and its copy in the channel where the command ran, both as its own messages (so later updates can reach them), and tells the caller alone ("Posted. A Treasurer approves it in the treasury channel; this channel shows the run without its buttons.", or "...shows the policy without its buttons."). What stays where it was: the empty-period line (nothing for a Treasurer to do), receipts (DMs), proposals and other private answers (Create pay run, Edit, Discard and Count who wrote are only ever on the proposer's own private answer), `/rolepay status run:` and `/rolepay policy show` (private, with their buttons: Approve policy and Discard on a draft, the link to a policy's own budget), the budget offer after an approval (private), the deposit address of `/rolepay fund new` (public on purpose, to share with the funder; its buttons are links to the Funding page and the explorer, which anyone may open), and the governance lines (pause, resume, mode), which carry no buttons. Rolepay has no notices today that are not tied to a run or a policy (no "budget running low" or "key expiring" message), so there is nothing else to route.
- **The copy** is `runMessage` with `mirror`: the same embed, the same words ("Pays at ... unless a member with @Treasurer vetoes it.", "Waiting for a member with @Treasurer to approve."), with no Approve, Cancel, Retry or Veto; the View transaction link stays once paid. A policy preview's copy is `policyMessage` with `mirror`: the same preview and its status ("Draft, version 1. Waiting for a member with @Treasurer to approve."), without Approve policy and Discard. Neither ever names the private channel (a mention of a channel people cannot see renders badly).
- **Both messages follow the run.** `RunNotices` keeps the message with the buttons (`message`, in the treasury channel) and the copy (`mirror`), on the KeyValueStore with the same 90 days. A button pressed in the treasury channel answers with its update and edits the copy in the same response's background (`Outcome.update.mirrors`); the payment job edits the copy each time it edits its own message; the policy notifier (`updateRunMessages`) and the recovery sweep edit both. So approved, paying, paid, failed, held, vetoed and cancelled all show on both.
- **Both messages follow the policy preview.** `RunNotices.policyPreview` keeps its two messages and the version they show in one record (`discord:policy-mirror:<policyId>`, the same 90 days). Approve policy or Discard pressed in the treasury channel edits the copy in the background the same way; pressed on a private `/rolepay policy show`, both. An approval, discard, edit or archive on the dashboard edits both (`updatePolicyMessages`, above). The status each shows: "Active. Approved by @Treasurer" with when and the next run, "Discarded by", "Version 1 was replaced by version 2, edited by", or archived. A discard, an edit or an archive settles the preview and its record is dropped: the replaced message never claims anything about the new version, which nothing in Discord would keep it in step with; an approved one is kept, so a later edit says it was replaced. Pause, resume and mode leave the preview as it was (in Discord they have their own public lines).
- **Choosing it.** On the dashboard's Overview, the Treasurer role picks one of the server's text channels, or None (below). With nobody having chosen (`unset`), Rolepay looks for a text channel named exactly "treasury" (any case; "treasury-old" is not it; core's `findTreasuryChannel`) when its first such message is about to be posted, or when a Treasurer opens the Overview; it posts its confirmation there ("Rolepay will post here what needs a Treasurer: policies and runs to approve, runs you can veto, and runs it holds."), which proves it can post there, and takes it with `useFoundTreasuryChannel` (audited, Rolepay as the actor). A channel it cannot post in is not taken. A Treasurer's choice, None included, always wins: Rolepay never picks by name again, except in place of a channel set that is gone.
- **When it cannot post there.** If the treasury channel refuses a new message (deleted, or Rolepay lost access: `forbidden` or `not_found`), the message goes where it would have gone without one, buttons included, as before (a policy preview: the command's answer, with Approve policy and Discard), the server logs a `treasury_channel` line (`unavailable`, with the code), and the lookup by name tries once in its place. If the message already in the treasury channel can be neither edited nor posted again, its copy takes the buttons over (it becomes the run's message and the copy is forgotten), so a Treasurer can still act. Nothing is lost either way.
- **Without one** (None, or none found), every message is posted exactly as before: one message, with its buttons, where it always went. While nobody has chosen, the lookup costs one Get Guild Channels per such message.
- **Permissions are unchanged.** Every button still checks the approver role from the signed interaction, wherever it is pressed: a treasury channel left visible to everyone shows the buttons again, and they are refused to anyone without the role. The channel's privacy is Discord's to set.

### Execution

Discord requires an answer within 3 seconds; paying can take longer. Approve and Retry enqueue an `ExecutionJob` on the **`ExecutionQueue` port**:

```ts
type ExecutionJob = { kind: 'execute_run'; guildId: string; runId: string; reply: { applicationId: string; token: string }; channelId: string | null }
interface ExecutionQueue { enqueue(job: ExecutionJob): Promise<void> }
```

`InProcessExecutionQueue` runs jobs in the background, one at a time per run, different runs in parallel. The job carries the review message's channel and ID too. The job (`createRunExecutor`) remembers where that message is (the **`RunNotices` port**, on core's KeyValueStore so it survives a restart), then calls `payRuns.execute`; while the outcome is `pending` it waits until `retryAfter` (plus a second of slack) and calls `reconcile`, up to 12 checks, then hands over to the recovery sweep; on `concurrent_update` (another worker holds or just changed the run) it reads the run again: a settled run is reported at once, one still being paid is followed with `reconcile` after a wait (never a new signature), one still `approved` (the other worker let go) is paid after the wait, so a contention never drops a run. One `job` log line per job: how it ended, milliseconds in all, split into `pay` (chain and database, waits included) and `discord`, plus `checks` and `contended`. It edits the message through the interaction webhook (tokens last 15 minutes; after that it posts to the channel as the bot), and the run's copy without buttons when it has one (the treasury channel), and once paid it DMs each payee a receipt through `DiscordRest`. Receipts go out at most once per run: whoever sends them first claims them in `RunNotices`. **After a restart** the job is gone, so the recovery sweep reports instead (`createRecoveryNotifier`): for each run it settled, it DMs the receipts (if nobody has) and edits the review message in its channel as the bot, or posts the result there if the message cannot be edited. A pre-flight failure (no active key, over the limit, revoked) leaves the run `approved` and shows the reason with a Retry button. Because `execute` is idempotent and the boot sweep recovers anything in flight, losing the in-process queue in a crash loses no money and pays nothing twice. A durable queue can replace it behind the same port.

## Renamed from payrun

The product was called payrun while it was built. What was already stored or posted under that name keeps working, and these stay as they are on purpose:

- **On chain.** The memo layout and its `"PR"` prefix bytes are unchanged, so earlier runs still reconcile.
- **The vault.** The HKDF labels `payrun:seal` and `payrun:fingerprint` derive the keys that open sealed bot keys and match link tokens. They never change; a known-answer test in `adapters/crypto/crypto.test.ts` holds them.
- **The database file.** The default is `rolepay.db`, but the server keeps using the repo-root `payrun.db` when it exists and `ROLEPAY_DB_PATH` is unset (`apps/server/src/env.ts`).
- **Settings.** Every `PAYRUN_X` is still read as `ROLEPAY_X` when that is unset or blank (`withDeprecatedEnvNames` in `config/env.ts`), and the server logs the deprecated names in use.
- **Discord.** Run buttons are now `rolepay:<action>:<runId>`; buttons already posted carry `payrun:` and still decode. The slash command changed from `/payrun` to `/rolepay`, so the commands are registered again.
- **Sessions.** The passkey-login record keeps its `payrun:passkey-login:` key in the KeyValueStore.

## Known limits and open decisions

- At most 50 lines per run (Tempo's 30M gas cap per tx at about 300k gas per first transfer to a fresh address, with a 2x margin). Raise only after a chain test at the new size.
- One active bot key per community; replacing it revokes the old one on chain. A policy can have one active key of its own besides (see Policy keys).
- A policy's own key, once revoked, stops that policy until it gets a new key: there is no switch back to the bot key's shared budget (archive the policy and write it again). The link to the policy's treasury page is a setup link, issued to the approver role (not Manage Server as well, as `/rolepay setup` requires): the page does nothing without the treasury passkey. All keys, the bot key and every policy key, are sealed in the same server vault: a full server compromise reaches all of them, each still capped by its own limit on chain. Payees are per community (the same person in two guilds registers twice).
- The run creator may also approve it (if they hold the approver role), by default: many small communities have one treasurer who also builds the runs, and refusing them would block the product. A community that wants four eyes runs `/rolepay setup separate_approver:true` (a treasurer only), and then `approve` refuses the creator with `creator_cannot_approve`.
- A change of approver role is answered ephemerally to the treasurer who made it; nothing is posted publicly yet. Moving it behind the treasury passkey on the setup page would make it as strong as a key change.
- No recipient allowlist by default; adding a payee to an allowlist needs a root-signed `setAllowedCalls` (a passkey prompt), which is why it is off in v1.
- Mainnet: guarded by `ROLEPAY_ALLOW_MAINNET=true`, and config also needs `ROLEPAY_PAYOUT_TOKEN` (USDC.e in `fly.app.toml`) and, without a sponsor, `ROLEPAY_FEE_TOKEN` (pathUSD). No sponsor is configured, so communities there start in `fee_budget` (see Fees) and payees pay about a cent per send from what they hold. A self-hosted relay (`Handler.relay`) or Tempo's hosted one (API key) would sponsor them. The runbook is `apps/server/MAINNET.md`.
- A fee budget that is not empty but smaller than one run's maximum fee passes the pre-flight (`checkKeyForRun` only checks it is positive) and the run then fails as `rejected` (retryable, nothing sent); the treasurer replaces the key with a larger budget.
- Live updates are per process (`InProcessLiveFeed`): with a second instance, a page sees only its own instance's events until it reconnects or reloads. Pages that are open also re-read on every event of their community (debounced), which is fine at this scale. A policy page's Latest run comes from core's policy runs, so a policy port that is not core's shows "No run yet".
- One amount per person in `/rolepay new` (with per-user overrides). A CSV or modal for many different amounts is later.
- Preferred stablecoins: the slippage cap is a server setting, not per community; a swap leg's cap is the sum of its lines' caps (one swap per token). The weekly totals count what people received, not what the swaps cost. An AI proposal still compares its total with what the bot key has left (only standing policies count the swaps at their maximum, `spendCap`), so a proposal just under the limit can become a run that the pre-flight holds before signing (`insufficient_limit`). Mainnet routing was not checked from here (only Moderato's RPC was used); a pair that does not route is held with `swap_no_route` before anything is signed. Turning the switch on without authorising a new key holds every run that swaps (`swap_not_authorized`), which the setup page says.
- Receipts are best effort: one that fails (closed DMs) is counted, not retried, and never sent twice.
- The treasury and payout token cannot be changed after registration (no service method for it yet).
- **The passkey domains.** `demo.rolepay.app` (the testnet demo for judges) and `web.rolepay.app` (mainnet), each with its own rpId (the host by default, `ROLEPAY_RP_ID` to override). Passkeys bind to the rpId for good, so the demo's passkeys never work on mainnet; a quick tunnel host is fine for testing only.
- A setup link is short-lived rather than single-use (see SetupLink). A recipient's claim link is single-use.
- The setup page's code is served by the bot server itself (see "The page signs what the treasurer typed"), so a fully compromised server could serve altered setup JavaScript. Accepted for the small mainnet pilot, where the loss is bounded by the treasury; on the roadmap: a separate static origin for the page that the bot server cannot change.
- "Use a wallet I already have" takes secp256k1 accounts (EOAs) only. Smart-contract wallets (ERC-1271, ERC-6492) and the Tempo Wallet's passkey accounts ("Sign in with Tempo") are next: the Accounts SDK has the connector (`tempoWallet()`) and viem's Tempo chain verifies a passkey signature envelope offline, but its default dialog is an iframe of wallet.tempo.xyz (a `frame-src` the CSP does not allow; scoping it to the claim page, or the SDK's popup mount, would do), what the wallet's `personal_sign` returns (the root passkey's signature or an access key's) was not confirmed against a live wallet, and the tests cannot reach it (THREAT-MODEL section 7). An own wallet has no `/account` page: the payee moves the money with that wallet, and chooses a preferred stablecoin with `/payee prefer`.
- A payee's passkey account (and the treasury) is a passkey bound to this server's host, so it is moved only through this server's account page; if the database's copy of the passkey's public key and the browser's memory of the account were both lost, the passkey could not sign again until that key is recovered (it is public on chain once the account has signed). The volume is snapshotted daily.
- The setup page signs with whatever passkey account the Accounts SDK has signed in on that browser; if it is not the treasury, the page asks for the treasury passkey and the server refuses the others anyway.
- AI proposals: the model can misread an instruction; the checks hold what they can prove wrong (sources, amounts, budget) and the treasurer reads the rest. Plain-text names in messages reach Anthropic as written. A pool (and a message-mode split) is shared among registered matches only. Proposals expire after a day. Criteria mode counts activity in any channel the bot can read, whoever proposes: proposers are the approver role or a role the approver chose, and only counts come back, never text.
- Standing policies: only the latest due period is run (no backlog after downtime, no backfill after a resume); a held run is not retried automatically (the next period runs as usual); a pool is shared among registered matches only; a policy posts in the channel where it was written (no command to move it yet); a policy created from the dashboard without a channel posts nowhere in Discord. A treasurer who approves an autopilot run by hand during its window (from `/rolepay status run:`) races a veto at the same instant; the run's own status is then the truth. Policy names are user text, so the audit stream refers to policies by ID. A daily policy (the testnet demo): `run_now` makes the next day's run at once and the scheduler then skips that day; a day where more than 50 people match is held (one run pays at most 50), and so is every day after it until fewer match (paying some by hand helps: paid people no longer match).
- Deposit addresses: the watcher attributes deposits in the payout token and the network's known USD stablecoins (`KNOWN_TOKENS`); another TIP-20 sent to a deposit address still lands in the treasury but is not recorded. A non-TIP-20 token, or a transfer on another chain, sent to a deposit address is lost (TIP-1022 forwards TIP-20 only); the Funding page and the Discord reply say so. One master per community, for good (registrations cannot be rotated on chain). Attribution says which address money arrived at, not who sent it. Deposits are read every 30 seconds, so the page lags by up to that.
- The dashboard reads at most 1,000 runs per page view and keeps its member cache in memory per process; dashboard sessions last eight hours whatever the activity. The member's server list is a snapshot from sign-in (sign out and in to refresh it); access itself is always the bot's live view.
- The treasury channel: a policy's author who holds only the proposer role and cannot see the treasury channel cannot press Discard there; a Treasurer discards the draft (in Discord or on the dashboard). A run or a policy preview made from Discord whose copy Rolepay cannot post where the command ran (no Send Messages there) is answered with the copy instead, which later updates do not reach. While nobody has chosen a channel, each message that needs a Treasurer reads the server's channels once (the lookup by name), and a Treasurer's Overview reads them on every view. Messages posted before a treasury channel was set keep their buttons where they are.
- On the dashboard: the mode form takes whole hours (minute windows are a Discord demo control); the Policies list shows "?" for how many people a policy matches now (its page works it out); the policy page reads Discord for the preview and the rule's names on every view.
- The WebAuthn endpoints are open (anyone can register a passkey with the server; a registration session never counts as the treasury's passkey, see Setup). POSTs to /webauthn, /claim, /setup and /dashboard, and every request under /auth/ (the Discord sign-in), are rate limited behind the `RateLimiter` port (`rateLimitGroup` in `packages/web/src/app.ts`; `defaultRateLimits` in `apps/server/src/compose.ts`: per client, by the last X-Forwarded-For hop or, behind Fly, by `Fly-Client-IP` (`ROLEPAY_CLIENT_IP_HEADER`), and per endpoint group overall), in memory per process. `POST /discord/interactions` limits only requests that fail the Ed25519 signature check, per client (see Guards at the edge): a valid one is never counted, and is refused only if its own address has just sent 10 invalid ones (Discord sends one, when the endpoint URL is saved, to check that it is refused). Junk from many addresses still costs one signature check each. Expired key-value rows read as absent and are swept on the recovery interval; request bodies over 1 MB are refused.
